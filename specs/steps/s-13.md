# Step 13 — Customer Context Service

## Objective

Implement the customer context builder: `GET /customers/:id/context` plus the internal `ContextService.buildForCase(caseId)` used by AI decisioning — producing a compact, allowlisted, size-bounded, tenant-isolated context object covering customer profile, payment/subscription/invoice/checkout summaries, recovery history, and communication history.

## Why this step exists

Spec 01 §9: "Do not pass the full database to the LLM." The context service is the privacy and token-cost boundary between raw operational data and the AI (spec 02 §2: aggregates approved context, enforces field allowlists, protects tenant boundaries). Every later AI call consumes exactly this object — its snapshot is what makes decisions auditable and reproducible.

## Requirement Coverage

- Spec 01 §9 Customer Context Service (shape + enforced properties: privacy, allowlists, size limits, freshness rules, tenant isolation)
- Spec 02 §2 Context Service boundary ("does not decide actions")
- Spec 03 §11 "LLM context allowlisted"

## Prerequisites

- s-06 repositories; s-04/s-05 tables; s-09 auth for the HTTP route

## Requirements

1. `buildCustomerContext({tenantId, customerId, opts})` → typed `CustomerContext` object.
2. Field allowlist constant defining exactly which columns may appear; anything not allowlisted cannot be included even by accident (typed projection, not delete-after-fetch).
3. Size budget: serialized context ≤ 8KB; over-budget triggers deterministic trimming priority list (documented).
4. Freshness rule: aggregates computed from live queries at build time; response carries `built_at`; cache in Redis 30s keyed `(tenant, customer, purpose)` where purpose ∈ {api_read, ai_decision} (ai_decision never served stale >60s).
5. HTTP route for dashboard/debugging with VIEWER+ access.
6. Redaction pass: emails→masked (`j***@d***.com`) unless purpose=api_read? NO — keep real email out of BOTH purposes except a dedicated `contact.email_masked` field; actual addresses flow only through messaging adapters via DB lookup at send time. This guarantees no PII enters prompts/logs.

## Technical Implementation

### Files

```text
apps/backend/src/modules/customers/
├── context/
│   ├── allowlist.ts        # single source of truth
```

### Output shape (matches spec 01 §9)

```json
{
  "built_at": "...",
  "customer": { "id","name","status","lifetime_value_minor","tenure_days","opted_out" },
  "payment_summary": {
    "succeeded_count_180d","failed_count_180d","last_success_at","last_failure_at",
    "last_failure_code","avg_amount_minor","total_paid_minor"
  },
  "subscription_summary": { "status","plan_name","amount_minor","renewals_count","past_due_events" },
  "invoice_summary": { "open_count","overdue_count","worst_days_overdue","total_overdue_minor" },
  "checkout_summary": { "active_carts","abandoned_count_90d","last_cart_value_minor" },
  "recovery_history": {
    "prior_cases","recovered_cases","stopped_cases","escalated_cases",
    "last_outcome":{"case_id","amount_recovered_minor","at":"..."},
    "retry_success_rate"
  },
  "communication_history": {
    "whatsapp_last_7d","email_last_14d","sms_last_7d",
    "last_contacted_at","reply_rate","opt_out_at"
  },
  "preferences": { "preferred_channel","language" }
}
```

### Trimming priority (when over 8KB)

Drop order: checkout_summary.details → invoice_summary.history → recovery_history.last_outcome → payment_summary.last_* timestamps → communication_history.reply_rate. Never drop: opted_out flag, prior case counts, last failure code, contact-frequency counters (these gate policy).

### Query pattern

All aggregates via indexed repository methods in ONE parallel batch (Promise.all) — target <100ms p95. No N+1 loops.

## Data Model Changes

None.

## API Contracts

```text
GET /customers/:customerId/context
Auth: session/api-key, role ≥ VIEWER
Query: ?purpose=ai_decision|api_read (default api_read)
200 → CustomerContext | 404 NOT_FOUND (cross-tenant id also 404 — no existence leak)
Headers: X-Context-Built-At, X-Context-Bytes
Rate limit: 120/min/key
```

Internal API: `contextService.buildForCase(caseId)` resolves case→customer then builds with purpose=ai_decision; throws CASE_NOT_FOUND / CUSTOMER_MISSING.

## State Transitions

Not applicable (read model). Cache invalidation hooks: opt-out change, new message sent, outcome recorded (explicit cache busts from those services when implemented).

## AI Behavior

This step DEFINES what the AI may ever see:

- Allowed: aggregates, counts, statuses, masked identifiers, amounts.
- Forbidden always: full emails/phones, addresses, card data, free-text notes, raw webhook payloads, other customers' data.
The zod schema doubles as the guardrail test contract (s-14 asserts prompt input validates against it).

## Reliability

Pure read path; Redis cache failures degrade to direct queries (WARN log). Any repo error → 503 CONTEXT_UNAVAILABLE rather than partial silent output.

## Security Considerations

Allowlist enforcement is type-level AND runtime-level (zod strict schema rejects unknown keys). Tenant isolation tested with cross-tenant fixture. Masking unit-tested against known PII patterns (email/phone regex sweep on serialized output must find zero matches except masked fields).

## Observability

Span `context.build{customer_id,purpose,bytes,durationMs}`; metric `context_build_duration_ms`, `context_bytes` histogram; warn if bytes>budget after trim.

## Tests

Unit: summarizers against synthetic rows (boundary dates/windows); trimmer drops in exact documented order; schema rejects injected extra field.
Integration:
- seeded customer with mixed history → exact expected JSON snapshot
- empty-history customer → zero-filled shape
- cross-tenant request → 404
- cache: second call within TTL hits cache (spy), opt-out bust works
PII sweep: serialized contexts for 50 seeded fixtures scanned by regex → no unmasked email/phone/card patterns.
