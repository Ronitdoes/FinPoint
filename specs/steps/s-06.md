# Step 06 — Migration Pipeline Hardening & Repository Layer

## Objective

Harden the migration workflow (advisory-lock, CI gate, seed-of-record structure) and implement the typed repository layer over the s-04/s-05 schema: one repository module per aggregate with explicit transaction support, guarded state-transition writes, and append-only enforcement for log tables.

## Why this step exists

Services (s-07 onward) must never hand-write SQL or touch `db` directly — scattered queries are how tenant scoping and financial invariants get lost. The repository layer is the only place where SQL, transaction boundaries, and conditional-update concurrency guards live. This is the last data-layer step; everything above it speaks domain objects.

## Requirement Coverage

- Spec 02 §16 repository layering (`packages/db → schema/, repositories/`)
- Spec 01 §21 "Financial actions must be idempotent" (guarded claims implemented here)
- Spec 01 §26 "migration checks" in CI
- Spec 02 §15 "Application queries should always scope by tenant"

## Prerequisites

- s-04, s-05 (schema exists)
- s-02 (config package supplies DATABASE_URL/DIRECT_URL)

## Requirements

1. `withTransaction()` helper exposing a `Tx` type accepted by every repository method (Drizzle transaction wrapper).
2. Repositories: tenants, users(+api_keys), customers, payments(+attempts), subscriptions, checkouts(+events), invoices(+events), events, risks, cases, decisions, actions, workflows(+events), messages(+deliveries,+responses), promises, human_tasks, policies(+versions,+evaluations), audit(+case_events), outcomes(+cost_entries), idempotency.
3. Guarded transition primitives on cases/actions/messages (conditional UPDATE … WHERE status IN (…) RETURNING id).
4. Append-only tables expose insert/select only.
5. Tenant scoping enforced by signature: every business-repo method takes `{ tenantId }` as first parameter — no exceptions.
6. Migration runner gains advisory lock + retry-once-on-serialization-failure; add `db:migrate:check` script for CI (fails if pending migrations exist).

### Key method contracts (representative — full set analogous)

```ts
// cases.repo.ts
createCaseInTx(tx, input): Promise<CaseRow>            // inserts case; relies on partial unique index
transitionCaseStatus(ctx, { caseId, from: CaseStatus[], to, reason? }): Promise<CaseRow | null>
  // UPDATE recovery_cases SET status=to, status_reason=..., closed_at=...
  // WHERE id=$case AND status = ANY(from) RETURNING *  → null means raced/invalid
findLiveCaseByObligation(ctx, { tenantId, sourceEntityType, sourceEntityId })
nextCaseNumber(tx, tenantId): number                   // SELECT ... FOR UPDATE on tenant row counter or advisory lock

// actions.repo.ts
insertAction(ctx, data)                                // unique idempotency_key violation surfaces as DuplicateActionError
claimActionForExecution(ctx, { actionId }): Promise<ActionRow | null>
  // UPDATE ... SET status='EXECUTING', started_at=now()
  // WHERE id=$id AND status IN ('APPROVED','PROPOSED') AND (scheduled_at IS NULL OR scheduled_at<=now()) RETURNING *
completeAction / failAction(ctx, { actionId, result?, error? })   // conditional on EXECUTING

// messages.repo.ts
insertMessage(ctx, data)                               // DuplicateMessageError on idempotency_key conflict
recordDeliveryEvent(...)                               // append-only

// events.repo.ts
insertEventIfNew(ctx, { source, externalEventId, ... }): Promise<{ event } | { duplicate: true }>
markProcessed / markFailed(...)

// outcomes.repo.ts
recordOutcomeInTx(tx, data)                            // ON CONFLICT (case_id) DO NOTHING + returning check

// idempotency.repo.ts
tryAcquire(ctx, { key, requestHash, ttlSeconds }): 'ACQUIRED' | 'IN_FLIGHT' | 'COMPLETED_DIFFERENT' 
complete(key, responseSnapshot) / releaseLease(key)
```

### Transaction boundaries (documented in each service-consuming repo)

| Operation | Boundary |
|---|---|
| Webhook accept: insert event row | single INSERT, autocommit |
| Case creation: risk upsert + case insert + case_event | ONE tx |
| AI decision persist | single INSERT |
| Action claim → provider call → complete/fail | claim is its own tx; completion is its own tx (provider call NEVER inside DB tx) |
| Outcome recording: outcome + cost rollup + case→RECOVERED | ONE tx |
| Policy rule update: new policy_version row + rules pointer flip | ONE tx |

### Connection pooling notes (write into repo README section)

- App pool via existing `postgres.js` client (`prepare:false` for pooler compatibility).
- Pool size: default 10 per API instance; worker uses Temporal activity concurrency to bound DB usage; document formula `pool_size ≈ concurrent_activities + headroom`.
- Migrations always use DIRECT_URL single connection (existing pattern).

### Concurrency primitives

- `nextCaseNumber`: `pg_advisory_xact_lock(hashtext(tenant_id || ':case_seq'))` inside the creation tx, then `SELECT max(case_number)+1`.
- All guarded updates return affected-row counts; services translate `null` into typed race errors rather than throwing raw SQL errors.

## State Transitions

`transitionCaseStatus` and `claimActionForExecution` are THE two choke points through which every later state change flows; unit tests must prove illegal transitions cannot occur even under concurrent calls (two parallel claims → exactly one winner).

## Reliability

- Idempotency: `tryAcquire` implements lease semantics — `IN_FLIGHT` after crash past `locked_until` becomes re-acquirable (lease expiry = visibility timeout).
- Retries: migration retry once on transient serialization failure; repository methods do NOT auto-retry (services own retry policies).
- Every repo returns plain rows mapped to domain entity types — no ORM leakage upward.

## Security Considerations

Tenant scoping at signature level; a lint rule (eslint no-restricted-syntax or code-review checklist item) flags any repository method missing `tenantId`.

## Observability

Add optional `onQuery` slow-query logging hook (>200ms logged with warning + first parameters redacted).

## Tests

Integration tests (run against composed Postgres from s-02, using test-scoped transactions rolled back per test):

- Parallel `createCaseInTx` ×10 same obligation → exactly 1 success, 9 constraint violations.
- Parallel `claimActionForExecution` ×2 → 1 non-null.
- `transitionCaseStatus` invalid pair → null + no row change.
- Insert-then-update attempt on audit/case_events table fails to compile (type-level).
- `tryAcquire` lifecycle: ACQUIRED → IN_FLIGHT (second caller) → COMPLETED_DIFFERENT with different hash.
- `recordOutcomeInTx` twice → second is no-op.
