# Step 23 — Workflow B: Checkout Abandonment

## Objective

Implement `CheckoutAbandonmentWorkflow`: inactivity timer → abandonment confirmation → risk/context/AI/policy → reminder → wait → purchase check → optional policy-approved incentive → purchase/stop, including the checkout.started ingestion path and completion race handling.

## Why this step exists

Surface 2 (spec 00 §4, spec 01 §15 Workflow B). Its distinctive difficulty is the *race*: customers complete purchases concurrently with the recovery workflow — every side effect must re-verify checkout state immediately before sending anything, and the workflow must stop instantly on purchase.

## Requirement Coverage

- Spec 00 Surface 2 sequence; spec 01 §15 Workflow B; spec 02 §11 example
- Spec 03 §1 Checkout abandonment = MVP required; §8 acceptance (purchase completes → workflow stops; abandoned past threshold → case may be created)
- Spec 02 §6 action subset for surface (no retries — no money movement initiated by us)

## Prerequisites

- s-22 patterns established; s-12 risk scorer supports CHECKOUT_ABANDONMENT; s-10 gateway handles checkout.completed events

## Requirements

1. Trigger path: `checkout.started` arrives via POST /events (merchant backend) or demo simulator → orchestrator creates a lightweight WATCH record (not a case yet) and starts the workflow with `{checkoutId}`.
2. Timer: default 30m inactivity (configurable per tenant); on fire, activity confirms still-abandoned via fresh DB read (status + last_activity_at).
   - completed meanwhile → workflow completes silently (no case ever created) ← acceptance test
3. Abandoned confirmed → risk scoring (high_checkout_intent rule) → case creation (DETECTED→…→IN_PROGRESS pipeline identical to s-17).
4. Round structure:

```text
reminder (EMAIL or WHATSAPP per decision) → wait(4h default)
purchase check:
  ├─ completed → RECOVERED (attribution WORKFLOW_LINKED to completed order/payment if linked,
  │              else ATTRIBUTION_WINDOW entry recorded by s-26 sweeper)
  └─ not yet   → incentive stage ONLY if initial AI+policy approved OFFER_INCENTIVE
                 send incentive message w/ link → wait(24h) → final check → stop
```

5. Incentive discipline: first contact NEVER contains discount (spec 03 Scenario B expectation: "discount = none initially"); incentive only as second touch and only within cap.
6. Purchase detection sources: checkout.completed webhook/event, payment.succeeded with matching source_ref, manual API confirm (demo).
7. Completion race guard: before EVERY send, transactional check-and-flag `checkout.recovery_contacted_at`; if completed_at set between check and send, abort send (best-effort window documented).

### Watch records

Stored in `checkouts` table itself using status=STARTED + `abandonment_workflow_started` metadata flag; no new table (documented rationale: single source of truth).

## Data Model Changes

None new.

## API Contracts

None new beyond existing /events ingestion. Signals: stop/external-checkout-completed/pause/resume.

## State Transitions

```text
WATCHING(timer) → CONFIRMED_ABANDONED → case DETECTED→…→IN_PROGRESS ⇄ WAITING
IN_PROGRESS → RECOVERED (purchase during window)
            → STOPPED   (window expired / opted-out / policy stop / already purchased race)
No ESCALATED except approval-required incentive path.
```

## AI Behavior

Decision scope: reminder channel/template choice, reminder timing suggestion (clamped 1–48h), whether incentive is warranted at all (recommendation only), incentive amount ≤ cap. Cannot create payment links here (surface subset excludes RETRY_PAYMENT/links? — links allowed per s-03 subset but MVP flow uses merchant's existing checkout URL passed as variable).

## Reliability

Idempotency: messages keyed per step (`{tenant}:{case}:{channel}:{template}:1|2`). Race guard above. Timer drift harmless (state re-read after wake). Duplicate checkout.started for same cart → single watch (source_ref unique).

## Security Considerations

Cart contents limited to allowlisted item summaries in templates; no customer PII beyond first name variable.

## Observability

Counters per stage (reminder_sent, incentive_sent, recovered_by_stage) feeding intervention-performance analytics; conversion latency histogram.

## Tests

```text
1. completes before timer      → workflow exits, NO case created
2. completes after reminder    → RECOVERED, exactly one reminder sent
3. full path with incentive    : abandoned→reminder→wait→no purchase→incentive(policy-allowed)→purchase→RECOVERED
4. incentive rejected by policy(amount>cap) → second touch skipped → STOPPED(NO_ACTION_ALLOWED)
5. race: purchase lands between state-check and send → send aborted (spy), workflow closes RECOVERED
6. duplicate started events    → one workflow
7. opt-out after reminder      → stop, no incentive
8. high-intent scoring         : cart ₹7,999 fixture → HIGH band (Scenario B parity)
```

## Definition of Done

- [ ] All 8 scenarios green incl. race-abort proof
- [ ] No-discount-first-touch invariant enforced by test
- [ ] Case creation deferred until true abandonment (acceptance test parity)
- [ ] Attribution rows produced for both linked and window cases (s-26 contract honored)
