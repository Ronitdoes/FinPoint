# Step 01 — Architecture Baseline & Implementation Contract

## Objective

Convert the four specification documents in `specs/` into a single, unambiguous implementation contract for this repository: a confirmed stack decision record, the target repository layout, cross-cutting engineering conventions, and a requirements-traceability matrix that every subsequent step links back to. No product features are built in this step.

## Why this step exists

The specs describe the *what* and the *why* (product vision in `00-brainstorm-and-product-vision.md`, build sequence in `01-implementation-0-to-100.md`, service boundaries in `02-architecture-and-domain.md`, MVP scope in `03-mvp-build-spec.md`). The repo already contains a Turborepo scaffold (Bun workspaces, `apps/backend` with a raw `Bun.serve` stub, `apps/frontend` Next.js shell, `packages/db` with an empty Drizzle schema). Before any code is written, the team needs one place that resolves every "which exact technology / which convention" question so later steps can reference decisions instead of re-debating them, and so a coding agent can execute steps s-02…s-35 without rediscovering context.

## Requirement Coverage

- Architectural contract: `AI = recommendation + interpretation; Policy = permission; Temporal = execution + durability; PostgreSQL = source of truth; Event bus = asynchronous propagation; Adapters = provider-specific execution; Dashboard = observation` (spec 02 §1)
- Core loop: Detection → Decision → Policy → Execution → Outcome → Learning (spec 00 §1)
- Bounded autonomy principle: AI recommends; deterministic infrastructure decides and executes (spec 00 §1, §8)
- MVP scope boundaries incl. "What NOT to build initially" (spec 01 §30, spec 03 §1)

None. This is the first step.

### Conventions to write into CONVENTIONS.md

- Module layout inside backend: `*.controller.ts` (routes/schemas), `*.service.ts` (business logic), `*.types.ts`; repositories live in `packages/db/src/repositories`.
- Errors: domain error classes with stable machine codes (`{ error: { code, message, details } }` envelope); Fastify error handler maps them to HTTP status.
- Logging: structured JSON logs via pino; mandatory fields `correlation_id`, `tenant_id`, `case_id` when present; never log secrets or full card/customer PII (allowlist).
- All async external calls define explicit timeout + retry policy at call site (no implicit defaults).
- Every DB write that changes business state happens inside an explicit transaction boundary owned by a service function.
- Branch naming `feat/<step-id>-<slug>`; commit messages reference step id (e.g., `s-07:` prefix).

## AI Behavior

Record the governing principles here once; later steps inherit them:

- The LLM may only: diagnose cause, rank interventions from the closed Action Catalog (spec 02 §6), draft template-parameter content within allowlists, and set stop conditions.
- The LLM may NEVER: move money, trigger retries itself, send messages itself, alter discounts beyond configured caps, contact opted-out customers, or choose actions outside the catalog.
- Every LLM output passes: JSON-Schema structural validation → semantic validation → policy evaluation before any execution path sees it.
