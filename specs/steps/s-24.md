# Step 24 — Workflow C: Overdue Invoice & Promise-to-Pay

## Objective

Implement `OverdueInvoiceWorkflow` (reminder ladder → response handling → promise-to-pay sub-flow → follow-up → payment/escalation) plus the promise-to-pay tracking lifecycle and dispute escalation handling.

## Why this step exists

Surface 3 (spec 00 §4, spec 01 §15 Workflow C, spec 02 §12). B2B invoices introduce: human-approval-required high values (Scenario C), promise-to-pay as a first-class state, disputes that must immediately stop automation, and longer multi-week cadences — the deepest test of durable execution.

## Requirement Coverage

- Spec 01 §15 Workflow C; spec 02 §12 example incl. response branching
- Spec 03 §1 overdue invoices + promise-to-pay required; Scenario C expectations
- Spec 03 §8 acceptance: high-value invoice incentive → human approval
- Spec 02 §5 customer events (promised_to_pay, payment_received) integration

## Prerequisites

- s-21 approvals, s-22/23 patterns, s-19 inbound responses (PROMISE_TO_PAY type), s-18 payment links

## Requirements

1. Trigger: invoice.overdue event (gateway-normalized or scheduler detecting due_at passage) → risk (days_overdue rules) → case pipeline.
2. Reminder ladder (policy-capped): day-0 polite reminder (EMAIL) → +3d follow-up (EMAIL or WHATSAPP per decision) → +7d final notice w/ payment link → then replan.
3. Response branches consumed via `customer.replied` signals bridged from s-19 webhooks:

```text
payment received      → RECOVERED (link WORKFLOW_LINKED to invoice payment)
promise made          → create PTP row → wait until promised_by_date(+grace 24h)
                        ├─ honored (invoice.paid)   → RECOVERED
                        ├─ broken                   → one follow-up → escalate if still silent
                        └─ expired                  → escalate
dispute signal        → immediate STOP_CASE(DISPUTED) + DISPUTE_REVIEW human task (automation halt)
no response           → next ladder step
```

4. High-value rule interplay: amount_at_risk > ₹100,000 ⇒ any OFFER_INCENTIVE/payment-link discount path REQUIRE_APPROVAL (POL-HIGHVALUE) — Scenario C parity test.
5. PTP lifecycle service: MADE→(HONORED|BROKEN|EXPIRED) with guarded transitions; honored records honored_payment_id; metrics feed Promise-to-pay Completion metric (spec 00 §9).
6. Dispute guard: invoice.disputed / chargeback event anywhere in flow → hard stop all automation for customer+obligation (policy POL-DISPUTE backstop).
7. Scheduler safety net: daily cron (worker-side) reconciles invoices OVERDUE with no case (missed webhook recovery) and PTPs past expiry.

## State Transitions

Case:

```text
IN_PROGRESS ⇄ WAITING(ladder waits)
IN_PROGRESS → RECOVERED (paid | PTP honored)
IN_PROGRESS → ESCALATED (broken/expired PTP, approval paths, repeated silence after final notice)
any → STOPPED (disputed, opted-out)
```

PTP: MADE→HONORED|BROKEN|EXPIRED (terminal).

## AI Behavior

Scope: reminder tone/template selection, cadence suggestions within policy caps, PTP-broken next-step recommendation, escalation package drafting (summary for finance team — text ≤500 chars, facts only, no promises). Cannot waive fees/discounts beyond cap; cannot extend promised dates unilaterally (human task for that).

## Reliability

Long waits (weeks) rely on Temporal durability — verified by time-skipped tests simulating 30 days in seconds. Webhook-miss tolerance via cron reconciler. Duplicate ladder steps impossible (message step keys). Dispute race: dispute arriving mid-send → send aborted by pre-send dispute recheck (same pattern as s-23 race guard).

## Security Considerations

Invoice amounts/totals visible only within tenant; escalation summaries exclude bank details; FINANCE role required for any manual financial reconciliation endpoints.

## Observability

Metrics: ladder_step_reached_total{step}, ptp_outcome_total{result}, days_to_recovery histogram (invoice surface), dispute_stop_total. Timeline entries at every branch decision.

## Tests

```text
1. full happy: reminder→reply PROMISE→child workflow→paid on date→RECOVERED (honored PTP linked)
2. broken promise path: no payment by grace end → BROKEN → follow-up → ESCALATED

4. dispute mid-ladder → instant STOP + task; subsequent ladder sends blocked

6. ladder cap enforcement: email counter blocks 4th contact even though ladder wants it

8. 30-day time-skipped run completes without timeout errors
9. paid-before-start (already PAID invoice event replay) → no case
```
