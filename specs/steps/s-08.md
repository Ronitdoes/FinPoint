# Step 08 — Observability Foundation (OpenTelemetry, Metrics, Structured Logs)

## Objective

Implement `packages/observability` and wire it into the API: OpenTelemetry tracing (auto-instrumentations for HTTP + pg), a metrics registry with the first core counters/histograms, correlation-ID propagation, and local OTLP export via Docker. Every subsequent step then emits spans/metrics through shared helpers instead of ad-hoc logging.

## Why this step exists

Spec 01 §20 requires instrumenting HTTP latency, workflow latency, LLM latency/tokens, provider latency/failures, policy rejections, recovery success — and correlating everything by `event_id`, `case_id`, `workflow_id`, `decision_id`, `action_id`. Instrumentation added *after* features are built is always partial; adding it now makes telemetry a one-liner at each future call site.

## Requirement Coverage

- Spec 01 §20 full section (instrument list, tooling, trace keys)
- Spec 03 §10 "Measure actual values rather than claiming them" (histograms from day one)
- Spec 02 §1 observability as a layer boundary

## Prerequisites

- s-07 (plugin pipeline; registration point reserved)

## Requirements

1. `packages/observability` exporting: `initTracing(serviceName)`, `getLogger(bindings)`, `metrics` registry helpers, `withSpan(name, attrs, fn)`, and typed metric instruments.
2. Tracing: NodeSDK/OTLP exporter, auto-instrument `@fastify/*` http + `postgres.js` (via otel pg instrumentation where compatible under Bun — fallback: manual span around repository tx helper).
3. Metrics (Prometheus-compatible via OTLP or `/metrics` endpoint):
   - `http_requests_total{route,method,status}` / `http_request_duration_ms` histogram
   - `db_query_duration_ms`
   - `events_ingested_total{source,type}` and `events_duplicate_total{source}`
   - `risk_calculations_duration_ms`, `policy_evaluations_total{result}`, `policy_evaluation_duration_ms`
   - `llm_calls_total{model,status}` , `llm_latency_ms`, `llm_tokens_total{kind}` (registered now, emitted in s-14)
   - `provider_calls_total{provider,op,status}`, `provider_latency_ms{provider,op}` (emitted s-18/s-19)
   - `workflow_started_total{type}`, `workflow_outcome_total{type,result}` (emitted s-20+)
4. Correlation: middleware copies inbound `traceparent`/`x-correlation-id`; all child log lines include it; domain event envelope carries `correlation_id`.
5. Local collector: add `otel-collector` service to compose (OTLP :4317/:4318) exporting to logs for dev; Grafana/Prometheus wiring deferred to s-34 but config files stubbed under `infra/grafana/`.

## Technical Implementation

```text
packages/observability/src/
├── index.ts
├── tracing.ts        # initTracing({ serviceName, otlpEndpoint }) idempotent per process
├── logger.ts         # pino instance factory; binds {tenant_id?, case_id?, event_id?, decision_id?, action_id?, workflow_id?}
├── metrics.ts        # prom-client registry OR @opentelemetry/api metrics — choose ONE (recommend prom-client for MVP simplicity)
└── span.ts           # withSpan helper wrapping async fn, recording error status
```

Design rule: **prom-client registry exposed at `GET /metrics`** on an internal port (or same port, route-level auth later in s-30). Rationale: Grafana scrape without collector dependency locally; OTel traces still exported via OTLP. Record choice as ADR-014.

Span attributes convention (write into CONVENTIONS.md):

```text
recovery.event_id, recovery.case_id, recovery.workflow_id, recovery.decision_id,
recovery.action_id, tenant.id, llm.model, provider.name, provider.operation
```

Bun compatibility note: some otel auto-instrumentations assume Node internals. Guard imports; if an instrumentation fails to load under Bun, fall back to manual spans at defined choke points (fastify onRequest hook, repositories tx helper, adapter call sites). Verify at implementation time and record results in ADR-014.

## Reliability

- Telemetry must never take down request path: exporter failures swallowed after warning (sampled); metrics registry writes are in-memory.
- Span creation guarded when tracing not initialized (unit tests run without collector).

## Security Considerations

- Span attributes/log fields must not contain customer PII beyond ids; enforce via logger redact list + review checklist.
- /metrics bound considerations documented; production exposure decided in s-30/s-34.

prom-client alongside OTel traces (dual-signal) rather than pure-OTel metrics — simpler local Grafana story and no collector hard dependency for the demo; revisit unification post-MVP.
