# Step 27 — Analytics Service & APIs

## Objective

Implement the analytics read layer: executive summary, recovery funnel, intervention performance, recovery time-series, and AI performance endpoints — all computed exclusively from authoritative tables (outcomes, cases, decisions, evaluations) with tenant scoping and documented query contracts for the dashboard.

## Why this step exists

Spec 00 §6 defines the dashboard's three views (executive/operations/AI) and §9 the full metric catalog; spec 03 §7 details overview cards, funnel, and intervention table. Analytics correctness rule (spec 01 §25) is inherited from s-26: these endpoints aggregate stored outcomes — never live UI state.

## Requirement Coverage

- Spec 02 §13 analytics APIs (summary, recovery, interventions)
- Spec 00 §9 metric set (financial/operational/AI/customer)
- Spec 03 §7 dashboard data requirements (this step = data; s-28 = rendering)

## Prerequisites

- s-26 outcomes; s-12 risks (risk-by-type); s-14/15 decisions (AI metrics); s-16 evaluations (rejections); s-19 messages (channel/customer metrics)

## Requirements

1. Query layer with materialized-friendly SQL views (`analytics.v_*` in a migration) so heavy aggregates don't scan hot tables at request time; refresh strategy: views are plain (MVP volumes) + optional REFRESH MATERIALIZED VIEW CONCURRENTLY cron stub.
2. Endpoints below; every number traceable to a table/column (doc table per endpoint).
3. Timezone: aggregates bucketed by UTC day; display TZ conversion client-side.
4. Cache: Redis 30s per (tenant, endpoint, params-hash) with explicit bust on outcome recording.

### Metric definitions (freeze now; tests lock them)

```text
Revenue at Risk        = SUM(amount_at_risk) cases opened_in_range NOT terminal-RECOVERED-at-query
Revenue Recovered      = SUM(outcomes.recovered_amount) recovered_at in range   [incl. STOPPED-late]
Recovery Rate          = Recovered / AtRisk (range-cohort basis documented: by open cohort)
Recovery Cost          = SUM(outcomes.recovery_cost) range
Net Recovered          = SUM(net_recovered)
Active Cases           = count(status ∈ {QUALIFIED…WAITING, IN_PROGRESS, ESCALATED})
Escalations            = transitions into ESCALATED in range
Avg Time to Recovery   = avg(recovered_at - opened_at) over outcomes
Policy Rejection Rate  = rejected action proposals / total evaluated actions
Decision Acceptance    = executed actions / recommended actions (COMPLETED decisions)
Recommendation→Exec    = EXECUTED actions / COMPLETED decision actions
AI Cost per Case       = LLM cost entries / decided cases ; per ₹ recovered variant
Intervention Success   = outcomes attributed to cases whose effective_actions included type T / cases attempted with T (per type table spec 03 §7)
Funnel                 = AtRisk(opened) → Qualified → Contacted(≥1 message) → Attempted(≥1 retry/link) → Recovered(outcome)
Opt-out / Reply rate   = customer_responses aggregates (customer view subset)
```

## Data Model Changes

Analytics views migration only (no base-table changes).

## API Contracts

```text
GET /analytics/summary?from&to           → financial + operational cards payload
GET /analytics/recovery?from&to&bucket=day|week
                                         → timeseries [{date, at_risk_minor, recovered_minor, net_minor}]
GET /analytics/interventions?from&to     → rows per action type: {type, cases, successes, recovered_minor}
GET /analytics/funnel?from&to            → stage counts
GET /analytics/risk-mix?from&to          → counts+value by risk_type/band
GET /analytics/ai?from&to                → decisions, acceptance, rejections, approvals, avg_decision_ms,
                                           cost_case_minor, cost_per_recovered_bps
Auth: role≥VIEWER all endpoints; FINANCE+ for cost-bearing fields (cost fields omitted otherwise — header flag documents it)
Errors: 400 bad ranges (>370d window), 403
```

## Reliability

Cache stampede guarded (single-flight). Slow-query budget 500ms p95 (spec 03 §10 normal reads); views keep scans off OLTP paths; indexes already exist from s-04/s-05 for range predicates.

## Security Considerations

Strict tenant predicate inside every view definition (tenant_id = current_setting('app.tenant_id') pattern via session var or parameterized views through repo layer — implementation must guarantee no cross-tenant row can appear even if route filter bugs; test proves it).
