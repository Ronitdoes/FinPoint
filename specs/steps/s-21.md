# Step 21 — Human Escalation & Approval Primitives

## Objective

Implement the human-in-the-loop subsystem: `human_tasks` lifecycle service, Temporal signal-based waiting (no polling), approval APIs, SLA timers, and the escalation paths that workflows and the policy engine invoke. Dashboard UI consumes these APIs later (s-28); this step delivers the complete backend capability.

## Why this step exists

Spec 01 §19 requires human_tasks for high-value invoices, policy approvals, disputes, compliance review, and repeated workflow failure — with dashboard actions Approve/Reject/Pause/Resume/Assign — and explicitly: "Temporal should wait for the human decision rather than polling." Bounded autonomy is meaningless without a real escape hatch to humans.

## Requirement Coverage

- Spec 01 §19 human escalation (task types + actions + wait semantics)
- Spec 02 §2/§4 ESCALATED state + human waits owned by workflow engine
- Spec 03 §8 acceptance: high-value invoice incentive → human approval required
- Spec 00 Pillar B: approval requirements as hard boundary

## Prerequisites

- s-05 human_tasks table, s-20 signals/waitForHumanDecision primitive, s-09 RBAC, s-17 escalate flow stubs

## Requirements

1. Task service: create (from workflow activity or API), assign, approve, reject, resolve, cancel; every decision records decided_by/decided_at/notes.
2. Workflow integration: `waitForHumanDecision` activity-less pattern — workflow uses `HumanApprovalSignal` with `Condition()` loop on task status mirror; approval/rejection resolves continuation.
3. On APPROVE of an APPROVAL-type task tied to case: case ESCALATED→IN_PROGRESS via guarded transition; pending action rows move APPROVAL_REQUIRED→APPROVED; workflow resumes executing them.
   On REJECT: actions → CANCELLED(reason=HUMAN_REJECTED); workflow proceeds to stop path (STOPPED unless other allowed actions remain).
4. SLA timers: sla_due_at set at creation per type default (APPROVAL=24h, DISPUTE_REVIEW=72h…); overdue sweep marks tasks OVERDUE flag + emits bus event `human-task.sla-breached` (dashboard badge + future notification hook).
5. APIs below with matrix from s-09 (approve = OPERATIONS+, manage-all = FINANCE+).
6. Re-escalation guard: repeated workflow failure auto-creates WORKFLOW_FAILURE task once per attempt-burst (dedupe window 1h).

### Signal flow

```text
workflow ──createHumanTask activity──► human_tasks row PENDING (temporal_signal_sent=false)
API approve/reject ──► row APPROVED|REJECTED (+audit) ──► signal workflow 'human-decision'
workflow Condition(taskResolved) resumes with outcome
```

Crash safety: if signal lost (worker down), workflow's Condition loop re-reads task status from DB every 60s heartbeat-check as recovery fallback — still event-driven first, polling only as crash-repair.

## Data Model Changes

Add `overdue_at TIMESTAMPTZ NULL` + `escalation_count INT DEFAULT 0` columns to human_tasks (migration).

## API Contracts

```text
GET  /human-tasks?status=&type=&assigned_to=&overdue=
     role≥VIEWER → list w/ case summary embed
GET  /human-tasks/:id                    detail incl. linked case/decision context
POST /human-tasks/:id/approve            OPERATIONS+ body {notes?} → 200 {status:'APPROVED'} | 409 resolved
POST /human-tasks/:id/reject             OPERATIONS+ body {notes REQUIRED} → REJECTED
POST /human-tasks/:id/assign             FINANCE+    body {assignee_user_id}
POST /human-tasks                        OPERATIONS+ manual creation {case_id,type,title,...}
POST /human-tasks/:id/cancel             FINANCE+    {reason}
All mutations audited; cross-tenant ids → 404.
```

## State Transitions

Task: PENDING→ASSIGNED→(APPROVED|REJECTED)|CANCELLED; PENDING/APPROVED-side effects as §3; terminal immutable.
Case interplay: ESCALATED --approve--> IN_PROGRESS; ESCALATED --reject--> STOPPED (or continue remaining actions).

## AI Behavior

AI may propose CREATE_HUMAN_TASK (in catalog) with title/description/priority — content validated (length caps, no contact info). AI cannot resolve tasks; decisions are USER-actor only (actor_type enforced).

## Reliability

Idempotent approve/reject (second call 409 not double-signal). Signal delivery at-least-once + DB-status fallback covers loss. SLA sweeper idempotent (flag once). Dedupe guard prevents task storms during provider outages.

## Security Considerations

Approve/reject require authenticated session users (never api-key for decisions — accountability); notes mandatory on reject (audit quality); assignment changes audited.

## Observability

Metrics: human_tasks_open gauge by type, approval_latency_ms histogram (decision time metric feeds spec 00 AI view), sla_breach_total. Timeline events HUMAN_TASK_CREATED / HUMAN_DECISION_RECORDED.

## Tests

Harness:
- workflow awaiting approval resumes on signal; rejects unwind cleanly
- worker restart between create and decision → Condition fallback picks up persisted status
Integration/API:
- full approve path flips action rows + case state exactly once (concurrent double-approve → one winner)
- reject with empty notes → 422
- RBAC matrix incl. api-key attempting approve → 403
- SLA sweeper flags overdue fixture + emits event once
- re-escalation dedupe under simulated repeated failures
