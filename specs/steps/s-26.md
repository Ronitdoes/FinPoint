# Step 26 — Outcomes, Attribution & Cost Model

## Objective

Implement the authoritative economics layer: `recordOutcome` shared service, the attribution engine (WORKFLOW_LINKED + ATTRIBUTION_WINDOW sweeper), cost rollups from `recovery_cost_entries` into case outcomes, and outcome read APIs. This makes "Recovered ₹X" a database fact, not a UI calculation.

## Why this step exists

Spec 01 §25: "Never compute recovery from dashboard UI state. Use authoritative outcome records." Spec 02 §8/§9 define the cost model and attribution discipline (not every later payment counts). Pillar D requires every case to answer how much was at risk/recovered/cost/net — this step builds exactly those records.

## Requirement Coverage

- Spec 01 §25 analytics correctness + attribution definition
- Spec 02 §8 recovery cost model; §9 attribution model fields
- Spec 00 §9 financial metrics source-of-truth
- Spec 03 §4 recovery_outcomes field parity

## Prerequisites

- s-05 outcomes/cost tables; s-18 fee capture; s-15 LLM costs; s-19 messaging costs hook; workflows calling recordOutcome (s-22–24)

## Requirements

1. `recordOutcome({caseId, paymentId, method})`:
   - tx: insert outcome (unique case_id conflict → idempotent no-op returning existing)
   - rollup recovery_cost = SUM(recovery_cost_entries.case) written into outcome.recovery_cost
   - transition case → RECOVERED (guarded) + timeline RECOVERY_RECORDED
2. Attribution engine:
   - WORKFLOW_LINKED: set synchronously by workflows when their own retried/link/checkout payment succeeds
   - ATTRIBUTION_WINDOW sweeper (hourly job): finds RECOVERED-pending cases? No — finds STOPPED/CLOSED cases whose obligation got paid within attribution_window_hours AFTER workflow start and without a competing live case owning it (spec 02 §9 four conditions implemented literally); inserts outcome w/ method=ATTRIBUTION_WINDOW; emits timeline entry
3. Cost completeness jobs: ensure every EXECUTED action has cost entries where applicable (messaging unit costs constant table; manual_handling optional via API later).
4. APIs: GET /outcomes?from&to&surface..., GET /cases/:id/outcome.
5. Net recovered / ROI computed at query time from stored columns only (net is generated column already).

### Attribution conditions (implemented as one guarded query + assertions)

```text
payment P attributes to case C iff:
1. same customer AND same financial obligation (source_entity link or provider refs)
2. P.paid_at ≥ workflow.started_at
3. P.paid_at ≤ started_at + attribution_window_hours
4. no OTHER live case owns that obligation at attribution time
```

## State Transitions

Case → RECOVERED exclusively through recordOutcome (single choke point). Sweeper never reopens closed cases; it only ADDS outcomes to cases already terminal-with-payment-later (STOPPED cases can gain late ATTRIBUTION_WINDOW outcomes — documented nuance: status stays STOPPED, money still counted).

Wait—clarify: spec's funnel expects recovered count from outcomes; a STOPPED case with late payment yields outcome row but case remains STOPPED. Analytics must count recovered_amount from outcomes regardless of case status. Encode in s-27 queries + test here.

## AI Behavior

None directly; AI cost entries (s-15) flow into rollups making AI Cost per Case computable.

## Reliability

Double-count prevention: unique(case_id) + unique(case_id,payment_id)? — single-outcome-per-case chosen (s-05); competing payments after outcome recorded are logged as `outcome.superseded_payment` WARN (no mutation). Sweeper idempotent by construction.

Concurrency: recordOutcome racing case STOPPED transition → guarded update decides winner deterministically (RECOVERED wins over STOPPED if simultaneous; encode precedence in transition guard).

## Security Considerations

Financial aggregates tenant-scoped; no cross-tenant rollups exposed.
