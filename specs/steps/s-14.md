# Step 14 — AI Decision Service: Core Decision Path

## Objective

Implement the controlled LLM decision pipeline behind `POST /ai/decide`: prompt registry with versioning, per-surface decision JSON schemas, an OpenAI-compatible client with structured outputs, strict output validation, timeout/retry/fallback semantics, and persistence of every attempt into `ai_decisions`. The service produces a *recommendation record* — it executes nothing.

## Why this step exists

This is the "Decision" stage of the core loop and the product's differentiator (structured LLM decisioning, spec 00 Phase 1). Spec 01 §10 defines the endpoint contract and the hard rule "Do not allow arbitrary tool names"; spec 02 §2 bounds the AI to diagnosis + ranking + content drafting. This step builds the mechanics; s-15 adds governance/evaluation/cost controls.

## Requirement Coverage

- Spec 01 §10 AI Decision Service (input/output contract)
- Spec 03 §5 MVP decision schema + allowed action list
- Spec 02 §2 AI responsibilities & prohibitions

- Spec 03 §9 SIMULATE_LLM_FAILURE hook

## Prerequisites

- s-03 (action catalog + AI_DECIDABLE_ACTIONS), s-12 (risk), s-13 (context)

## Requirements

1. Prompt registry: versioned prompt templates per surface (`payment_failure@1`, `checkout_abandonment@1`, `invoice_overdue@1`) stored as TS constants with hash; `prompt_version` recorded on every decision row.
2. Decision schema (zod + JSON Schema export for provider structured-output) matching spec 03 §5 exactly, extended with confidence per diagnosis and per-action rationale strings.
3. Client: OpenAI-compatible chat completions with `response_format: json_schema`; configurable base URL/model/key from config; request timeout 20s (target typical <5s); 2 retries on transient (429/5xx/network) with exponential backoff+jitter.
4. Validation pipeline: structural (JSON Schema) → semantic (actions ∈ surface's AI_DECIDABLE_ACTIONS, params valid per catalog, delay bounds, confidence ∈ [0,1], stop_conditions enum) → sanity (at least one action OR STOP_CASE).
5. Failure ladder: malformed after N=1 repair retry → status INVALID_OUTPUT → rule-based fallback generator produces deterministic recommendation → status FALLBACK_RULE_BASED. Total path never exceeds ~30s.
6. Persistence: EVERY call persists ai_decisions row (COMPLETED | INVALID_OUTPUT | FALLBACK_RULE_BASED | FAILED) with input_snapshot (the redacted context actually sent), raw output, tokens, latency.
7. Endpoint `POST /ai/decide` (internal, role ≥ OPERATIONS or workflow principal) returns the decision record — no side effects beyond persistence.

### Input contract

```json
POST /ai/decide
{
  "case_id": "uuid",                     // required — service loads case+risk itself
  "risk_id": "uuid",                     // optional override validation
  "purpose": "CASE_OPENING"|"REPLAN"     // replans allowed mid-workflow
}
```

Service assembles: `{ recovery_case, risk (incl. factors), customer_context }` — the exact spec 01 §10 triple. Context fetched via s-13 builder (guaranteed allowlisted).

### Output decision record (validated shape)

```json
{
  "diagnosis": { "cause": "insufficient_funds|stale_card|bank_decline|network_issue|
                          price_objection|distraction|waiting_for_payday|unknown",
                 "confidence": 0.91,
                 "rationale": "<=240 chars" },
  "actions": [
    { "type": "RETRY_PAYMENT", "delay_hours": 24, "rationale": "...", "params": {...} }
  ],
  "stop_conditions": ["PAYMENT_SUCCEEDED","OPTED_OUT","MAX_RETRIES"]
}
```

Constraints enforced semantically: ≤3 actions; delay_hours ∈ [1,168] for RETRY_PAYMENT; OFFER_INCENTIVE params.amount_minor ≤ policy constant (re-checked by s-16); STOP_CASE must be alone; template names validated against messaging template registry ids (s-19).

### System prompt invariants (encoded once, tested)

```text
- You are a revenue recovery analyst. You RECOMMEND; you cannot execute anything.
- Choose only actions from the provided ALLOWED_ACTIONS list for this case type.
- Prefer zero-cost interventions before incentives; incentives require explicit amounts ≤ cap.
- If evidence is insufficient, set cause='unknown' with low confidence and recommend CREATE_HUMAN_TASK.
- Never invent identifiers, templates, or fields outside the schema.
```

### Fallback recommender (deterministic)

```text
PAYMENT_FAILURE: risk HIGH/CRITICAL & first failure → [RETRY_PAYMENT(24h), SEND_WHATSAPP(payment_retry_notice)]
                 retries ≥2 → [CREATE_HUMAN_TASK]
CHECKOUT:        high intent → [SEND_EMAIL(cart_reminder)]
INVOICE:         overdue ≥7d → [SEND_EMAIL(invoice_reminder), CREATE_PAYMENT_LINK]
plus stop_conditions defaults per surface
```

## API Contracts

```text
POST /ai/decide
Auth: session role≥OPERATIONS | worker principal (api-key scope ai:decide)
Body: { case_id, purpose? }
Responses:
  200 { decisionId, status:'COMPLETED', diagnosis, actions, stop_conditions,
        latency_ms, model, prompt_version }
  200 { decisionId, status:'FALLBACK_RULE_BASED', ...same shape, fallback:true }
  404 CASE_NOT_FOUND | 409 CASE_TERMINAL | 422 CONTEXT_INVALID | 503 LLM_UNAVAILABLE(after fallback also failed)
Idempotency: caller may send Idempotency-Key → same-key repeat returns ORIGINAL decision row (no new LLM spend).
```

## State Transitions

Case side-effect free here. Decision statuses:

```text
(attempt) → COMPLETED
          → INVALID_OUTPUT → (repair) → COMPLETED | FALLBACK_RULE_BASED
          → (transport exhausted) → FALLBACK_RULE_BASED | FAILED
```

## AI Behavior

Responsible for: diagnosis.cause/confidence, ranked actions within surface subset, template selection from registry, stop conditions, bounded rationale text.
NOT allowed: executing anything; contacting anyone; choosing actions outside subset; exceeding caps; multi-step planning beyond returned list; memory across calls (stateless).
Confidence handling: value persisted; threshold enforcement is POLICY territory (s-16: confidence <0.6 ⇒ REQUIRE_APPROVAL for money-touching actions). Documented handoff.
Tool usage: none. No function-calling. Structured output only.
Guardrails: schema+semantic validators above; context allowlist upstream; policy downstream.
Fallback behavior: deterministic recommender (above) — recovery loop never blocks on LLM health.
Token/cost considerations: max_tokens 800; context trimmed to budget (s-13); usage captured into row + metrics; cost computed via price table constant.
Logging: input snapshot stored REDACTED; never log raw completions at INFO (DEBUG only, sampled).
Evaluation strategy: dataset harness in s-15 replays golden cases against registry versions.

## Reliability

Timeout 20s hard; retries only on transient; circuit breaker (5 consecutive failures → open 60s → all calls go straight to fallback while open). SIMULATE_LLM_FAILURE=true forces timeout path in dev/tests (spec 03 §9).

## Security Considerations

Endpoint not public; api key scope ai:decide separate from events:write. Prompts contain only s-13-sanitized data. No customer PII in logs (mask sweep test re-used).

## Observability

Metrics: llm_calls_total{model,status}, llm_latency_ms, llm_tokens_total{kind}, fallback_total{reason}; spans llm.request / ai.decide linking case_id+decision_id.

## Tests

Unit: schema accepts spec §5 example verbatim; rejects unknown action/template/out-of-range delay/confidence>1; prompt builders embed full allowlist subsets; hash stability.
Client tests (mocked transport): timeout→retry→success; 429 backoff; non-transient 400 no-retry; circuit opens.
Integration:
- happy seeded case → COMPLETED row + endpoint payload matches row
- SIMULATE_LLM_FAILURE → FALLBACK_RULE_BASED row, endpoint 200 with fallback:true
- malformed completion fixture → INVALID_OUTPUT then repair then fallback
- Idempotency-Key replay returns original row (no second LLM call — counter assert)
- terminal case → 409
