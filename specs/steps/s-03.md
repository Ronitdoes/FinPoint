# Step 03 — Shared Domain Package (`@repo/domain`)

## Objective

Implement the framework-free business vocabulary of the platform: entities (TypeScript types), enums, the canonical internal event envelope, the RecoveryCase state machine with an explicit transition table, the closed Action Catalog, policy limit constants, and money/amount helpers. This package is imported by backend, worker, and frontend — it must have zero runtime dependencies on Fastify, Drizzle, Temporal, or any provider SDK.

## Why this step exists

Spec 01 §1 ("Define the domain") mandates defining business vocabulary before infrastructure. Spec 02 §1 requires that no component silently takes over another layer's responsibility — a shared domain package is how that boundary is enforced in code. Every later step (schema s-04/s-05, risk engine, AI schemas, policy rules, workflows) consumes these exact types and enums, so drift is impossible.

## Requirement Coverage

- Spec 01 §1 core entities: Customer, Payment, Subscription, Checkout, Invoice, RevenueRisk, RecoveryCase, RecoveryAction, Workflow, Message, PromiseToPay, Policy, AuditLog, RecoveryOutcome
- Spec 01 §12 / spec 02 §4 Recovery case state machine
- Spec 02 §5 event taxonomy; spec 01 §6 event envelope
- Spec 02 §6 action catalog; spec 03 §6 policy limits & stop conditions

## Prerequisites

- s-01 (ADR-009 money, ADR-011 time conventions)

## Requirements

1. New workspace `packages/domain` (pure TypeScript, `main`/`exports` pointing at `src/index.ts`, matching existing repo style).
2. Enums exactly as specified (see below) exported as both const objects and union types.
3. Event envelope type + zod schema for runtime validation.
4. State machine module: transition table + `assertTransition(from,to)` pure function.
5. Action catalog type + per-action parameter schemas (zod).
6. Money helpers: `formatMinorUnits(amount, currency)`, `parseAmountToMinorUnits(input)`.
7. Stop-condition enum and policy-limit constants (`MAX_PAYMENT_RETRIES=3`, `MAX_WHATSAPP_PER_7_DAYS=2`, `MAX_EMAIL_PER_14_DAYS=3`, `MAX_AUTO_DISCOUNT_MINOR=500_000` paise i.e. ₹500, `HIGH_VALUE_APPROVAL_MINOR=10_000_000` paise i.e. ₹100,000).

### Event envelope (must match spec 01 §6)

```json
{
  "id": "evt_uuid",
  "type": "payment.failed",
  "occurred_at": "2026-08-23T10:30:00Z",
  "source": "razorpay",
  "tenant_id": "tenant_123",
  "customer_id": "cus_123",
  "entity_id": "pay_123",
  "entity_type": "PAYMENT",
  "payload": {},
  "correlation_id": "uuid"
}
```

Zod schema enforces: `type` ∈ event-type taxonomy, ISO datetime strings, non-empty ids, payload object. Producers may attach optional `traceparent`.

### State machine transition table (spec 02 §4)

```text
DETECTED        → QUALIFIED | STOPPED            (STOPPED: unqualifiable, e.g., already recovered elsewhere)
QUALIFIED       → DECISION_PENDING | STOPPED
DECISION_PENDING→ POLICY_REVIEW | FAILED         (FAILED: AI unavailable after fallbacks)
POLICY_REVIEW   → IN_PROGRESS | ESCALATED | STOPPED
IN_PROGRESS     → WAITING | RECOVERED | STOPPED | ESCALATED | FAILED
WAITING         → IN_PROGRESS | RECOVERED | STOPPED | ESCALATED
ESCALATED       → IN_PROGRESS | RECOVERED | STOPPED   (post human decision)
RECOVERED | STOPPED | FAILED                → terminal
```

`assertTransition` throws `IllegalTransitionError { from, to }`; also export `TERMINAL_STATUSES = [RECOVERED, STOPPED, FAILED]`.

### Action catalog parameters (examples to encode)

- `RETRY_PAYMENT`: `{ attempt_number int ≥1 }`
- `CREATE_PAYMENT_LINK`: `{ amount_minor bigint>0, currency, expires_in_hours }`
- `SEND_WHATSAPP` / `SEND_EMAIL` / `SEND_SMS`: `{ template: string, variables: Record<string,string|number>, language? }`
- `OFFER_INCENTIVE`: `{ kind: 'DISCOUNT'|'COUPON', amount_minor ≤ MAX_AUTO_DISCOUNT_MINOR }`
- `REQUEST_PAYMENT_METHOD_UPDATE`: `{ link_url? }`
- `CREATE_PROMISE_TO_PAY`: `{ promised_amount_minor, promised_by_date }`
- `CREATE_HUMAN_TASK`: `{ task_type, title, description, priority }`
- `PAUSE_CASE` / `STOP_CASE`: `{ reason }`

Unknown action names fail validation — this is the structural guarantee behind spec 01 §10 "Do not allow arbitrary tool names."

## AI Behavior

Exports `AI_DECIDABLE_ACTIONS` ⊂ action catalog per surface:

```text
PAYMENT_FAILURE       : RETRY_PAYMENT, CREATE_PAYMENT_LINK, SEND_WHATSAPP, SEND_EMAIL,
                        REQUEST_PAYMENT_METHOD_UPDATE, CREATE_HUMAN_TASK, STOP_CASE
CHECKOUT_ABANDONMENT  : SEND_EMAIL, SEND_WHATSAPP, OFFER_INCENTIVE, CREATE_HUMAN_TASK, STOP_CASE
INVOICE_OVERDUE       : SEND_EMAIL, SEND_WHATSAPP, CREATE_PAYMENT_LINK, OFFER_INCENTIVE,
                        CREATE_PROMISE_TO_PAY, CREATE_HUMAN_TASK, STOP_CASE
```

The AI prompt layer (s-14) receives only its surface's subset; policy engine (s-16) re-checks against the full catalog anyway (defense in depth).

## Reliability

Pure functions only; no I/O. `assertTransition` is deterministic and unit-testable without DB.

## Security Considerations

No PII fields beyond identifiers inside entity types used for AI context are defined here — context allowlisting happens in s-13.

## Tests

Unit tests (pure): envelope schema accepts/rejects representative payloads; every legal transition passes `assertTransition`, every illegal pair throws (exhaustive matrix test generated from the table); action parameter validation incl. unknown-type rejection; money rounding/truncation rules; enum ↔ spec-text parity snapshot test (guards accidental enum drift from the spec).
