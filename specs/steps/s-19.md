# Step 19 — Messaging Adapters & Delivery Ledger (WhatsApp, Email, Mock)

## Objective

Implement `packages/integrations/messaging`: the `MessagingProvider` interface, WhatsApp Cloud API + SMTP/email-API adapters + Mock, a template registry with variable allowlists, the send pipeline that persists `messages` rows idempotently before dispatch, and delivery-status webhook ingestion updating the ledger.

## Why this step exists

Customer contact is the other irreversible action class: duplicate messages destroy trust and violate contact-cap policies. Spec 02 §2 assigns messaging to adapters only; spec 03 §1 requires WhatsApp (or mocked) + email; spec 01 §14 defines the interface. The ledger also powers policy counters (`whatsapp_sent_7d`, `email_sent_14d`) and the timeline.

## Requirement Coverage

- Spec 01 §14 MessagingProvider interface + adapters
- Spec 03 §2 MockMessagingProvider; §1 email required, WhatsApp yes-or-mocked
- Spec 01 §21 no double notifications; spec 02 §7 contact frequency rules rely on ledger
- Spec 00 §9 customer metrics (opt-out rate, reply rate → responses capture here)

## Prerequisites

- s-05 messages tables, s-06 repos, s-10 pattern for webhook ingestion (delivery callbacks), s-08 metrics

## Requirements

1. Interface exactly:

```ts
interface MessagingProvider {
  sendTemplate(input: SendTemplateInput): Promise<SendResult>;   // {providerMessageId, acceptedAt}
  registerStatusWebhook?: ...                                      // adapter-specific
}
```

2. Adapters: WhatsAppAdapter (Cloud API template messages), EmailAdapter (transactional provider or SMTP), MockMessagingProvider (logs + scriptable failures).
3. Template registry `templates/{whatsapp,email}/`: ids like payment_retry_notice, cart_reminder, invoice_reminder, ptp_confirmation — each with declared variables + language variants; AI-selected template names validated against registry in s-14.
4. Send pipeline `sendCaseMessage({caseId, channel, template, variables})`:
   - derive idempotency key `{tenant}:{case}:{channel}:{template}:{step}` where step = sequence within case
   - INSERT messages row QUEUED (unique conflict ⇒ return existing, skip dispatch)
   - policy counters already checked upstream (s-16); defense-in-depth recheck inside pipeline (cheap query)
   - dispatch via adapter w/ timeout 10s, retry ×2 network-class only
   - update SENT/FAILED; write message_delivery_events
5. Status webhooks `POST /webhooks/whatsapp` + `/webhooks/email` (signature/secret verified per provider) → DELIVERED/READ/BOUNCED/REJECTED transitions + events.
6. Inbound replies `POST /webhooks/whatsapp` (same endpoint, message-received payloads) → customer_responses rows + bus event `customer.replied` / `customer.opted_out` (STOP/UNSUB parsing for opt-out).
7. Opt-out handling: sets customers.opted_out=true immediately + emits event; all future sends blocked by policy AND pipeline recheck.

### Variable allowlist enforcement

Variables passed to adapters must match registry declaration exactly (extra keys rejected); values stringified from primitives only; customer contact addresses resolved from DB at send time (never taken from AI/context objects).

## Data Model Changes

None new.

## API Contracts

```text
POST /webhooks/whatsapp
Headers: x-hub-signature-256 (verify against WHATSAPP_VERIFY_SECRET)
Body: Meta statuses/messages payload
200 quickly always (after verification) | 401 invalid signature

POST /webhooks/email        token-in-path auth; provider status payload → ledger

GET /messages?case_id=&channel=&status=
Auth role≥VIEWER → redacted list (content preview masked per allowlist)
```

## State Transitions

Message: QUEUED→SENT→(DELIVERED→READ|BOUNCED|REJECTED)|FAILED. Terminal immutable; late duplicates of status events append delivery_events without changing terminal state.
Inbound response types: REPLY|OPT_OUT|PROMISE_TO_PAY|COMPLAINT|OTHER (PTP rows created by invoice workflow s-24 upon PROMISE_TO_PAY).

## AI Behavior

AI may select template ids and compose variable VALUES only from allowlisted fields (order id, amount, dates, link). It never supplies contact addresses and cannot bypass caps. Content constraints (no promises of refunds, no legal statements) enforced via template fixed text + variable slots only — free-form body generation disabled at MVP (documented).

## Reliability

No-double-send anchors: messages.idempotency_key unique + pre-dispatch recheck of policy counters. Provider timeout → mark FAILED (not UNKNOWN — messaging safe to retry manually via new key if workflow chooses). Webhook replays idempotent by (provider_message_id, status, timestamp) natural dedupe into events table.

## Security Considerations

Signature verification constant-time; phone/email stored as provided but rendered masked in reads; STOP keyword processing logged with actor=PROVIDER; no message bodies in traces.

## Observability

Metrics messaging_sent_total{channel,status}, messaging_latency_ms{channel}; spans send.dispatch{template}; opt-out counter alert-worthy later (s-34).

## Tests

Contract suite across providers:
- happy send → QUEUED→SENT(+DELIVERED via webhook fixture)
- duplicate pipeline call same step-key → single provider hit (spy)
- provider 500 → FAILED after retries; workflow-visible error
- SIMULATE_MESSAGE_FAILURE injection honored
- status webhook bad signature → 401 nothing written; valid → transition applied; replay ignored
- inbound STOP → opted_out=true + customer.opted_out event + subsequent sends rejected by recheck
- cap recheck: 3rd email in 14d blocked even if policy layer skipped
Template tests: every registered template renders with sample vars across languages; unknown var rejected.
