# Step 18 — Payment Provider Adapters (Stripe, Razorpay, Mock)

## Objective

Implement `packages/integrations/payments`: the `PaymentProvider` interface, three adapters (Stripe, Razorpay, Mock), an idempotency-aware execution service wrapping adapter calls with timeouts/retries/metrics, and the payment-status refresh path that lets workflows learn outcomes.

## Why this step exists

Spec 01 §14 mandates provider interfaces so "provider-specific logic never leaks into orchestration," and spec 02 §14 requires each adapter to carry explicit idempotency. Payment retry is the highest-stakes action in the system — double charging is the cardinal sin this architecture exists to prevent. The Mock adapter additionally enables the entire demo without real money (spec 03 §2).

## Requirement Coverage

- Spec 01 §14 integration adapters (interface + StripeAdapter/RazorpayAdapter)
- Spec 03 §2 MockPaymentProvider + mock mode
- Spec 01 §21 idempotency for financial actions
- Spec 02 §8 payment processing cost category (fee capture hook)

## Prerequisites

- s-04 payments/attempts tables, s-06 repos, s-02 config keys, s-08 metrics

## Requirements

1. Interface exactly:

```ts
interface PaymentProvider {
  retryPayment(input: RetryPaymentInput): Promise<RetryPaymentResult>;
  createPaymentLink(input: CreatePaymentLinkInput): Promise<PaymentLinkResult>;
  getPaymentStatus(id: string): Promise<PaymentStatus>;
}
```

2. Adapters: StripeAdapter (PaymentIntents confirm w/ saved PM or off-session), RazorpayAdapter (payments retry via order/link APIs), MockPaymentProvider (scripted outcomes + failure-injection switches).
3. Execution service `executeRetryPayment({caseId, attemptNumber, ...})`:
   - derives idempotency key `{tenant}:{case}:RETRY_PAYMENT:{attempt}` (spec 01 §21)
   - inserts payment_attempts row REQUESTED (unique key conflict ⇒ duplicate call detected → return existing outcome)
   - claims action row (guarded) BEFORE provider call
   - calls adapter with same idempotency key forwarded to provider where supported (Stripe idempotency header)
   - resolves attempt SUCCEEDED/FAILED/UNKNOWN; UNKNOWN triggers status-poll loop
4. Timeout budget per call 15s; retries ONLY for network-class errors ×2; HTTP 4xx from provider = definitive result not error.
5. Status refresh: poll getPaymentStatus up to N=6 times over 60s for UNKNOWN; final states written to payments + attempts.
6. Fee capture: adapters return provider fee when available → recovery_cost_entries(PAYMENT_PROCESSING).
7. Failure injections honored: SIMULATE_PAYMENT_TIMEOUT forces hang→timeout path (spec 03 §9).

```text

  default            : succeed after first FAILED attempt, fail second (configurable)
```

### Adapter specifics

```text
Stripe   : POST /v1/payment_intents/:id/confirm  header Idempotency-Key
           fees from balance transaction on success
Razorpay : create payment link / retry via orders API w/ receipt=key; webhook confirms async
           → adapter returns ACCEPTED_ASYNC + getPaymentStatus polls
```

Both map provider decline codes → internal failure taxonomy (insufficient_funds, stale_card, bank_decline, do_not_honor…).

## State Transitions

Attempt: REQUESTED→(SUCCEEDED|FAILED|UNKNOWN); UNKNOWN→(SUCCEEDED|FAILED) via polling; terminal immutable.
Action interplay: claim sets EXECUTING before call; completion/failure updates after; crash between claim and completion leaves EXECUTING → sweeper in s-31 reconciles via getPaymentStatus (never blind re-execution).

## AI Behavior

Adapters are pure executors — zero AI involvement possible (no import).

## Reliability

Idempotency matrix:

```text
same key twice (process crash after provider accepted) → provider dedupes (Stripe) /
attempt-row unique check short-circuits (all providers) → NEVER two charges
concurrent claims → guarded UPDATE single winner
provider timeout → attempt stays UNKNOWN + polled, not retried blindly
non-retryable declines → attempt FAILED immediately, no retry storm
retry policy: network errors ×2 backoff 1s/2s full jitter; then surface failure upward
DLQ n/a (workflow activity retry policies own outer loops, configured s-20)
```
