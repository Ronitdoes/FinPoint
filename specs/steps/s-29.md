# Step 29 — Demo Mode, Simulation Endpoints & Seed Data

## Objective

Implement mock-mode wiring end to end, the four simulation endpoints (`POST /demo/payment-fail`, `/demo/payment-succeed`, `/demo/checkout-abandon`, `/demo/invoice-overdue`), failure-injection switches as runtime controls, and deterministic seed data at spec volumes including the three named demo scenarios.

## Why this step exists

Spec 03 §2 mandates the app run without live providers; §3 defines exact seed scenarios A/B/C with expected outcomes; §24 lists seed volumes (1,000 customers, 2,500 payments, 300 failed, 250 active + 150 abandoned checkouts, 180 overdue invoices, 100 cases across risk bands/states). This step makes the whole platform demonstrable and CI-testable without external dependencies — the acceptance harness for s-30…s-35 depends on it.

## Requirements

1. Provider resolution honors MOCK_PROVIDERS=true: Stripe/Razorpay adapters swapped for MockPaymentProvider; WhatsApp/Email → MockMessagingProvider (records everything, sends nothing).
2. Simulation endpoints create REAL provider-shaped webhook deliveries through the actual gateway path (not direct service calls) so the entire ingestion→recovery chain is exercised:

```text
POST /demo/payment-fail        body {tenant_id?, customer_ref?, amount_minor?, provider?}
  → synthesizes customer+payment if needed → POSTs signed webhook to own /webhooks/{provider} (loopback)
POST /demo/payment-succeed     body {payment_id | provider_payment_id} → success webhook (+signals workflows)
POST /demo/checkout-abandon    body {customer_ref?, cart_value_minor?, age_minutes?} → checkout.started via
  POST /events then forced-abandonment event advancing the timer state
POST /demo/invoice-overdue     body {customer_ref?, amount_minor?, days_overdue?} → invoice.overdue webhook
Auth: OPERATIONS+ session OR demo api-key scope `demo`; DISABLED entirely when MOCK_PROVIDERS=false (410)
```

3. Failure-injection switches (env from s-02) exposed additionally as runtime toggles for demos: PATCH /demo/injections {simulate_payment_timeout?, simulate_message_failure?, simulate_llm_failure?, simulate_duplicate_webhook?} — writes to Redis w/ TTL 15min; adapters/LLM client read-through (env remains fallback default).
   SIMULATE_DUPLICATE_WEBHOOK=true causes next simulated delivery to send twice concurrently (proves idempotency live).
4. Seed script `packages/db/src/seeds/demo.ts` + CLI (`bun run db:seed`):
   - volumes per spec §24 with realistic distributions (amounts log-normal-ish, timestamps spread 90d, decline-code mix, channel mix)
   - 100 recovery cases spanning LOW/MEDIUM/HIGH/CRITICAL and states recovered/stopped/escalated/waiting incl. outcomes + cost entries so analytics are non-empty on first boot
   - Scenarios A/B/C created exactly per spec §3 fixtures (CUS-001/CUS-002/CUS-003) in pristine pre-trigger state where expected outcome must be *produced by the demo run*, plus one already-completed A-variant for dashboard richness
5. Idempotent re-seed: `db:seed --reset` truncates tenant-scoped demo data safely (never touches users table of real deployments — guarded by tenant slug check).

## AI Behavior

SIMULATE_LLM_FAILURE toggle drives fallback path visibly during demos (AI card shows FALLBACK badge) — proving bounded autonomy survives model outage in front of an audience.

## Reliability

Loopback webhooks go through signature verification (dev secrets from env) — no bypass paths exist even in demo mode (security invariant kept). Duplicate-webhook toggle gives live proof of dedupe for Scene-level Q&A.

## Security Considerations

Demo endpoints hard-disabled in production builds (config guard + route registration skip, tested); demo api-key cannot be minted when MOCK_PROVIDERS=false; loopback signer uses dev-only secrets documented as such.

## Observability

Each simulation logs a single structured DEMO line (refs + scenario tag); metrics unchanged (they're real traffic).

## Tests

- Each endpoint happy-path integration test asserting downstream artifacts (case created, workflow started) within poll window.
- Toggle lifecycle: set→behavior changes→TTL expiry resets.
- Duplicate toggle → single case under concurrent double-send.
- Seed determinism: two reseeds produce identical content hashes (excluding timestamps-by-design list).
- Scenario parity harness (extends s-22–24 suites): running A/B/C through simulators yields spec §3 expected bands/actions/policy results.
- Production-build guard test: routes absent when flag false.
