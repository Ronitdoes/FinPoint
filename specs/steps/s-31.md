# Step 31 — Resilience, Chaos & Concurrency Testing

## Objective

Execute the aggressive failure-testing program from spec 01 §21 as an automated, repeatable suite: duplicate webhooks, out-of-order events, provider/LLM timeouts, Redis/Postgres/Temporal failures, worker crashes mid-flight, browser-refresh/network-retry analogues, payment-succeeds-after-workflow-retry — proving financial idempotency and system self-healing under every listed condition.

## Why this step exists

Spec 01 §21 enumerates fourteen failure scenarios and demands they be "tested aggressively," with the hard invariant "Financial actions must be idempotent." Feature-step tests covered happy paths plus targeted failures; this step builds the dedicated chaos harness (fault-point injection + infrastructure kill drills) and locks results into CI-runnable suites so resilience is a maintained property, not a one-time demo.

## Requirement Coverage

- Spec 01 §21 full scenario list
- Spec 03 §9 failure-injection switches (exercised at scale)
- Spec 00 Pillar C durable execution (crashes, retries, duplicates, downtime, long waits, human delays)

## Prerequisites

- s-29 simulators + injections; full stack operational under compose; s-20 fault-point hooks

## Requirements

1. Fault-point harness: deterministic breakpoints in activities/services (env `FAULT_POINTS=claim:after_provider_call` style) enabling process-kill exactly between side effects — implemented via pre/post hooks registered in activity framework (no scattered ifdefs).
2. Infrastructure kill drills (scripted, compose):
   - `docker restart redis` during active rate-limit/cache use → degraded-not-dead behavior, recovery
   - Postgres connection drop (pause container 30s) → pool reconnects, in-flight tx fail cleanly retryable
   - Temporal worker SIGKILL mid-workflow round → workflow resumes from history correctly
   - Redpanda unreachable → producer buffers/fails per policy; consumers resume with backlog drain
3. Scenario matrix automation (all §21 items) with assertions on: no duplicate charges/messages/cases/outcomes; state converges; alerts/metrics reflect incidents.
4. EXECUTING-stuck sweeper: reconciliation job for actions claimed but never completed (crash window): resolves via provider status query; NEVER blind re-executes; completes/fails rows accordingly.
5. Backlog drain benchmark: enqueue 5k mixed events while bus down → bring up → measure drain time + zero loss/duplicates.

### Invariant assertions library

`assertInvariants(tenantId)` scans: payments↔attempts consistency, message uniqueness by key, single live case per obligation, outcomes ≤1/case, cost entries ≥ LLM-minimum for decided cases — reused by every scenario.

### Scenario acceptance highlights

```text
duplicate webhook ×50 concurrent     → 1 case, N≥1 DUPLICATE responses, metrics consistent
out-of-order succeeded→failed→failed → final SUCCEEDED; regression counter incremented twice
worker SIGKILL after claim,before provider call → attempt row REQUESTED→ resolved once post-resume;
                                                 provider called EXACTLY once (mock spy)
late success after STOPPED(MAX_RETRIES) → attribution sweeper records outcome (s-26 path), case stays STOPPED
opt-out midway between rounds        → remaining sends suppressed; workflow stops cleanly
```

Chaos runs only against dev/test tenants; compose admin scripts refuse to target prod-shaped env vars.

## Observability

Each drill asserts expected metric movements (e.g., provider_failures_total spike, dlq_total after poison). Post-drill report artifact (JSON) attached in CI summary.

## Tests

The scenarios ARE the deliverable. CI strategy: fast subset (duplicates, ordering, LLM faults) every push; full infra-kill matrix nightly via compose profile flag.
