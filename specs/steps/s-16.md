# Step 16 — Policy Engine

## Objective

Implement `packages/policy` and its API surface: deterministic evaluation of AI-recommended actions against hard rules (retry caps, contact frequency caps, discount caps, opt-out, disputes, approval thresholds), rule versioning with immutable snapshots, an append-only evaluation log, and endpoints `POST /policy/evaluate`, `GET /policies`, `POST /policies`, `PATCH /policies/:id`.

## Why this step exists

This is the layer the LLM can never override ("The LLM never overrides this layer", spec 01 §11; "Policy = permission", spec 02 §1). Every outbound customer contact and money-touching action must pass through here before execution. Deterministic rules make autonomous behavior bounded, auditable, and testable — the core of Pillar B (bounded autonomy).

## Requirements

1. Evaluator `evaluate(input): PolicyResult` — pure function over `(case snapshot, proposed actions, customer state, counters, active rule versions)`:
   - per-action verdict ALLOW | REJECT(reason codes[]) | REQUIRE_APPROVAL(reason codes[])
   - overall result ALLOWED | REJECTED | REQUIRE_APPROVAL
   - effective_actions = allowed actions (possibly with clamped params, e.g., incentive reduced to cap → recorded as ADJUSTED)
2. Seeded default rules (tenant_id NULL) exactly matching MVP constants:

```text
POL-OPTOUT          opted_out = true ∧ action ∈ {SEND_EMAIL,SEND_WHATSAPP,SEND_SMS}      → REJECT
POL-DISPUTE         dispute_open = true                                                   → REJECT (all)
POL-MAXRETRY        retry_count ≥ 3 ∧ action=RETRY_PAYMENT                                → REJECT
POL-WA-CAP          whatsapp_sent_7d ≥ 2 ∧ SEND_WHATSAPP                                  → REJECT
POL-EM-CAP          email_sent_14d ≥ 3 ∧ SEND_EMAIL                                       → REJECT
POL-DISCOUNT        OFFER_INCENTIVE amount > MAX_AUTO_DISCOUNT(₹500)                      → REJECT
                    amount ≤ cap but confidence gate true                                 → REQUIRE_APPROVAL
POL-HIGHVALUE       amount_at_risk > ₹100,000 ∧ action ∈ {OFFER_INCENTIVE,CREATE_PAYMENT_LINK} → REQUIRE_APPROVAL
POL-CONFIDENCE      requiresApproval(decision) (s-15 hook)                                → REQUIRE_APPROVAL
POL-PAYMENT-SUCCESS payment status SUCCEEDED                                              → REJECT all (stop condition)
```

3. Counters sourced from messages/payments repos (contact caps) — computed at evaluation time, not cached stale.
4. Versioning: PATCH creates new policy_versions row (snapshot+version+1); evaluator always loads active versions atomically per evaluation; every evaluation logs to policy_evaluations with version ids.
5. Rule definition JSONB schema (field path / op / value / applies_to) interpreted by a tiny safe expression matcher — no eval(), no user-supplied code.
6. Endpoints below; admin mutations FINANCE+; evaluate endpoint internal (worker principal or OPERATIONS+).

None new. Seed script writes policy_rules + first policy_versions for the 9 defaults (idempotent by rule code).

## API Contracts

```text
POST /policy/evaluate
Auth: worker principal (scope policy:evaluate) | session role≥OPERATIONS
Body: { case_id, actions:[{type,params}], decision_id? }
200 → result above (+evaluationId, latency_ms)
404 CASE_NOT_FOUND | 422 VALIDATION

GET /policies                       role≥VIEWER → list w/ enabled flag + active version
POST /policies                      FINANCE+    create tenant-scoped custom rule
PATCH /policies/:id                 FINANCE+    {enabled?, definition?, name?} → new version; audit entry
GET  /policies/:id/versions         FINANCE+    version history
Errors: 403 FORBIDDEN | 422 VALIDATION | 409 CONCURRENT_VERSION
```

## State Transitions

Not a stateful entity itself, but verdicts drive downstream transitions:

```text
action PROPOSED ──ALLOWED──► APPROVED(executable)
       ├─REJECTED──► POLICY_REJECTED (terminal; case may STOP if no actions remain)
       └─APPROVAL_REQUIRED──► human task path (s-21)
```

## AI Behavior

Relationship enforcement point: even a perfect LLM recommendation is inert without ALLOW here; conversely REJECT cannot be appealed by re-prompting (evaluator only sees structured facts). Clamping (ADJUSTED) is the ONLY mutation of AI params permitted anywhere in the system — and it never exceeds platform caps.

## Reliability

Target <50ms p95 (spec 03 §10): counters use covering indexes; evaluation pure & allocation-light; no network inside evaluator.
Failure behavior: on internal error evaluating, FAIL CLOSED (no execution) with POLICY_EVALUATION_FAILED — never open.

## Security Considerations

Custom rule definitions constrained by matcher whitelist (fields, ops); definitions validated against JSONB schema; tenant rules cannot reference other tenants' fields; mutations audited.

## Observability

Metrics from s-08 wired: policy_evaluations_total{result}, duration histogram; rejection reasons counter (feeds dashboard AI view "Policy Rejections", spec 00 §6).

## Tests

Unit: each rule table-driven (boundary values at caps ±1); combined-rule precedence; clamp-to-cap produces ADJUSTED not REJECT when within cap after clamp; matcher injection attempts rejected.
Integration:
- evaluate persists policy_evaluations row w/ correct version ids + latency
- PATCH bumps version; next evaluation uses new snapshot; old evaluation rows unchanged
- opt-out customer: any contact action REJECTed end-to-end
- retry_count=3 fixture: RETRY rejected while EMAIL still allowed
- high-value invoice: REQUIRE_APPROVAL path returns required_approval=true
- fail-closed: forced DB error during counter fetch → error result, nothing executable
Perf smoke: 500 evaluations avg <50ms.
