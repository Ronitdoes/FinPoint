# Step 17 — Recovery Case Orchestration Pipeline

## Objective

Implement the case lifecycle service that turns a qualified risk into an executing recovery: idempotent case creation, the qualification pipeline (risk → context → AI decision → policy evaluation → action rows → Temporal start), case read/control APIs (`GET /cases`, `GET /cases/:id`, pause/resume/escalate/stop), and full state-machine enforcement with timeline emission.

## Why this step exists

Spec 01 §12 defines this exact pipeline ("event → find/create recovery case → attach risk record → load customer context → request AI decision → policy check → start workflow") and its central invariant: "A duplicate webhook must not create duplicate recovery cases." The RecoveryCase is the join point for everything the dashboard shows; this step is where Detection hands off to Execution.

## Requirement Coverage

- Spec 01 §12 Recovery Case orchestration + idempotency requirement
- Spec 02 §3 canonical case object fields; §4 state machine
- Spec 02 §13 cases API surface (list/get/pause/resume/escalate)
- Spec 01 §17 timeline events (emitted here via case_events)
- Spec 03 §8 acceptance tests (one case per failed payment; duplicate webhook → no dup)

## Prerequisites

- s-12 risk engine, s-14/s-15 AI decisioning, s-16 policy engine — reachable as services
- s-06 repos incl. guarded transitions; s-11 bus (consumes risk.calculated)

## Requirements

1. Consumer group `orchestrator` on `revenue-events.v1` handling `risk.calculated`:
   - skip if subject already has a live case (partial unique index as backstop)
   - create case in ONE transaction: case row DETECTED→QUALIFIED + risk attachment
   - publish `case.opened` to trigger asynchronous pipeline (no long work inside consumer handler)
2. Pipeline runner `runPipeline(caseId)` with persisted stage ledger and resumability:

```text
QUALIFIED        → DECISION_PENDING : context build (s-13) + ai.decide (s-14)
DECISION_PENDING → POLICY_REVIEW    : policy.evaluate on recommended actions (s-16)
   ├─ REJECTED (all actions)         → STOPPED(reason=POLICY_ALL_REJECTED) + timeline POLICY_REJECTED
   ├─ REQUIRE_APPROVAL               → ESCALATED + APPROVAL human task (s-21 primitives)
   └─ ALLOWED                        → persist recovery_actions rows (APPROVED, idempotency keys set)
                                      → start Temporal workflow via s-20 client interface
                                      → IN_PROGRESS + timeline WORKFLOW_STARTED
```

3. Case control APIs calling workflow signals (pause/resume) and direct escalation/stop.
4. Idempotent pipeline: re-invocation for same case resumes from first incomplete stage.
5. Every transition through guarded `transitionCaseStatus`; every step writes case_events (+ audit_logs for mutations).

### Creation idempotency detail

```text
tryCreateCase({tenantId, sourceEntityType, sourceEntityId, riskId, amountAtRisk,...}):
1. SELECT live case for obligation → return {existing}
2. INSERT in tx (DETECTED) then transition QUALIFIED same tx; on 23505 race → re-select → {existing}
3. publish case.opened (correlation preserved)
```

### Stage ledger

`recovery_cases.metadata.pipeline[] = [{stage:'CONTEXT'|'AI_DECISION'|'POLICY'|'ACTIONS'|'WORKFLOW', status:'DONE', at, ref}]` appended transactionally per completion.

## API Contracts

```text
GET /cases
Auth role≥VIEWER. Query: status?, risk_type?, customer_id?, min_amount?, opened_from/to?, limit≤100, cursor
200 {items:[CaseSummary], nextCursor}

GET /cases/:id
200 canonical case + embedded risk summary, latest decision (summary only),
    latest policy evaluation, actions[], workflow{id,status}, outcome? | 404 (incl. cross-tenant)

POST /cases/:id/pause     OPERATIONS+ 202 {status:'WAITING'} | 409 ILLEGAL_TRANSITION
POST /cases/:id/resume    OPERATIONS+ 202 {status:'IN_PROGRESS'}
POST /cases/:id/escalate  SUPPORT+    202 → ESCALATED + HUMAN_TASK(GENERAL)
POST /cases/:id/stop      FINANCE+    body {reason} → STOPPED (cancels workflow signal)
All control ops audited; terminal cases → 409 CASE_TERMINAL
```

## State Transitions

Introduced here (machine from s-03):

```text
DETECTED→QUALIFIED→DECISION_PENDING→POLICY_REVIEW→IN_PROGRESS
POLICY_REVIEW→ESCALATED|STOPPED
IN_PROGRESS⇄WAITING
non-terminal→ESCALATED|STOPPED(manual, reason mandatory)
DECISION_PENDING→FAILED(reason=NO_DECISION_AVAILABLE) when AI+fallback both fail
```

## AI Behavior

Operational enforcement of the constitution:
- AI called once per purpose (idempotency key caseId+purpose) with only allowlisted context.
- Output treated strictly as proposals; policy verdict authoritative; workflows receive ONLY effective_actions.
- No code path connects AI module directly to adapters (lint boundary test added).

## Reliability

Concurrency: simultaneous risk.calculated ×N same subject → exactly one case. Crash mid-pipeline → resume via ledger. Workflow start idempotent by Temporal workflow-id (proved in s-20). Consumer retries safe (all steps anchored).

## Security Considerations

Least-privilege controls (stop = FINANCE+ due to financial impact); actor recorded in audit_logs; tenant scope on every read/write.

## Observability

Spans `case.pipeline.{stage}` linked by case_id; metric `pipeline_stage_duration_ms{stage}`; funnel counters opened→qualified→decided→allowed→started (consumed by s-27).

## Tests

Integration:
- failure event → one case; event replay ×5 concurrent → still exactly one
- happy path → IN_PROGRESS with APPROVED action rows == policy effective_actions (incl. clamp case)
- all-rejected fixture → STOPPED + POLICY_REJECTED entries
- approval fixture → ESCALATED + PENDING APPROVAL task
- SIMULATE_LLM_FAILURE w/ fallback disabled → FAILED(NO_DECISION_AVAILABLE)
- pause→resume round-trip
API: filters/pagination, tenant isolation, RBAC matrix on control ops, terminal-case 409s.
