# Step 07 — Backend Application Skeleton (Fastify)

## Objective

Replace the raw `Bun.serve` stub in `apps/backend` with a production-shaped Fastify application: app factory + server entrypoint, plugin pipeline (config, logger, database, error handling, request-id/correlation, CORS, body limits), health/readiness endpoints, graceful shutdown, and the module registration convention that all later feature modules plug into.

## Why this step exists

The Event Gateway and all internal APIs (spec 01 §7, spec 02 §13) run on Fastify. Building the skeleton once — with correct logging, error envelopes, lifecycle, and module conventions — means every subsequent endpoint step only writes route modules. The existing `/health` behavior must be preserved so nothing regresses.

## Requirement Coverage

- Spec 01 §3 backend stack (Fastify + TypeScript)
- Spec 02 §2 Event Gateway responsibilities boundary (this step builds the host; s-10 fills it)
- Spec 03 §10 performance targets (webhook <300ms, API p95 <500ms — latency measurement hooks land here)
- Spec 01 §26 "Use Docker for API" groundwork

## Prerequisites

- s-01 (ADR-002), s-02 (`@repo/config`), s-06 (repositories available for readiness checks)

## Requirements

1. Fastify 5 instance created via `buildApp()` factory (testable without listening).
2. Server entrypoint `src/server.ts` handles signals (SIGTERM/SIGINT), closes server → drains DB pool → exits.
3. Plugins in order: requestContext (request-id + correlation), logger, cors, rateLimit placeholder, db, errorHandler, otel (registered but no-op until s-08).
4. Route modules auto-registered from `src/modules/*/routes.ts` via a registry array.
5. Endpoints live after this step: `GET /health`, `GET /api/health` (alias, preserves current behavior), `GET /ready`, `GET /version`.
6. JSON body limit 256KB; strict JSON parsing; 404 handler returns canonical error envelope.
7. Keep Bun as runtime; ensure no Bun-only APIs inside framework code.

## Technical Implementation

### Files

```text
apps/backend/src/
├── index.ts                 # thin re-export kept for bun --watch compat OR deleted; update package.json scripts
├── server.ts                # entrypoint: buildApp().listen({ port, host })
├── app.ts                   # buildApp(opts): FastifyInstance
├── plugins/
│   ├── context.ts           # requestId (uuid), correlationId (from x-correlation-id or new), child logger binding
│   ├── logger.ts            # pino config: level from config, redact paths [req.headers.authorization,
│   │                        #   req.headers.stripe-signature, '*.password', '*.apiKey']
│   ├── db.ts                # decorate fastify with repositories bundle + tx helper
│   ├── error-handler.ts     # maps DomainError subclasses → status; zod errors → 422; fallback → 500 (no stack leak)
│   ├── rate-limit.ts        # @fastify/rate-limit wired to Redis store; global defaults; per-route overrides later
│   └── shutdown.ts          # tracks in-flight requests; close timeout 20s
├── lib/
│   ├── errors.ts            # DomainError base + codes: VALIDATION, UNAUTHENTICATED, FORBIDDEN, NOT_FOUND,
│   │                        # CONFLICT, IDEMPOTENCY_IN_FLIGHT, RATE_LIMITED, INTERNAL
│   └── routes.ts            # module registry
└── modules/
    └── meta/
        ├── routes.ts        # /health /ready /version
        └── meta.service.ts  # readiness = DB ping + redis ping + temporal reachability (best-effort, cached 5s)
```

### Error envelope mapping (from ADR/s-01 contract)

```text
VALIDATION(zod)          → 422 {error:{code:'VALIDATION', details: issues}}
UNAUTHENTICATED          → 401
FORBIDDEN                → 403
NOT_FOUND                → 404
CONFLICT / DUPLICATE_*   → 409
IDEMPOTENCY_IN_FLIGHT    → 409 with Retry-After header
RATE_LIMITED             → 429 with Retry-After
INTERNAL (unhandled)     → 500 (message generic; details logged with requestId)
```

### Logging standard

pino with `base: { requestId, correlationId }`; serializers strip authorization/signature headers; one line per request at INFO with `{method,url,status,durationMs}`.

### Graceful shutdown sequence

```text
SIGTERM → stop accepting → wait in-flight (max 20s) → close DB pool → flush logs → exit 0
```

Temporal worker process gets its own shutdown in s-20 (separate binary).

### Performance instrumentation hooks

- `onResponse` hook records duration histogram metric placeholder (`http_request_duration_ms`) — real metrics export lands in s-08.
- Route-level `config.requestTimeoutMs` default 10s; webhook routes will override to 25s budget internally (still ack fast).

## API Contracts

```text
GET /health      → 200 {status:'ok', uptime, timestamp}   (no auth)
GET /api/health  → same                                    (compat alias)
GET /ready       → 200 {checks:{db:'up',redis:'up'}} | 503 {checks:{db:'down'...}}
GET /version     → 200 {name, version, gitSha, env}
```

All responses use canonical envelope on error. No auth required for these four.

## Reliability

- Health vs readiness split: LB uses /health (process alive); orchestrators/compose use /ready (dependencies reachable). Prevents routing traffic into a boot-broken instance.
- Unhandled rejection/exception handlers log-and-exit (let supervisor restart; never run half-dead).

## Security Considerations

- CORS: allowlist origins from config (dev: localhost:3000; prod: dashboard domain) — not `*`.
- Trust proxy enabled only behind known proxy config flag.
- Body limit + strict parser reduce parser-abuse surface early.

## Observability

Request logs + duration hook now; OpenTelemetry SDK activation is s-08's job but plugin registration point exists here.

## Tests

- App-factory unit tests: unknown route → 404 envelope; validation error shape; error handler maps each DomainError code to expected status.
- Integration: /ready returns 200 against composed infra, 503 when DATABASE_URL points nowhere.
- Shutdown test: send SIGTERM during in-flight request → response completes then process exits within timeout.
