# Step 12 — Risk Engine v1 (Deterministic Scoring)

## Objective

Implement the deterministic, rule-weighted risk engine: it consumes revenue-risk events from the bus, computes a 0–100 score with a per-rule factor breakdown and LOW/MEDIUM/HIGH/CRITICAL band, persists `revenue_risks`, emits `risk.calculated` case events, and exposes `GET /risks` + `GET /risks/:id`.

## Why this step exists

Detection is stage one of the core loop (spec 00 §1) and the first consumer of the event bus — it proves the pipeline works end to end. Spec 01 §8 mandates starting deterministic (rule weights), deferring ML; spec 02 §2 forbids the engine from messaging customers or issuing discounts: it only detects, scores, and records.

## Requirement Coverage

- Spec 01 §8 Risk Engine v1 scoring table + bands
- Spec 02 §2 Risk Engine responsibilities/non-responsibilities
- Spec 02 §5 detection triggers across payment/checkout/invoice/customer events
- Spec 00 §9 metrics feeding later analytics (risk by type chart, s-27/s-28)

## Prerequisites

- s-11 (consumer framework), s-05 (revenue_risks schema)

## Requirements

1. Consumer group `risk-engine` subscribed to `revenue-events.v1`; handles trigger events:
   - payment.failed → assess payment-failure risk
   - checkout.abandoned / inactivity-derived abandonment → checkout-abandonment risk
   - invoice.overdue → invoice-overdue risk
   - payment.succeeded / invoice.paid / checkout.completed → close/expire related open risks
2. Scoring exactly per spec 01 §8 base table (configurable weights via policy-style config row, defaults below).
3. Band mapping: LOW <40, MEDIUM 40–59, HIGH 60–84, CRITICAL ≥85.
4. Factor breakdown persisted in `factors JSONB` (explainability for UI "why at risk").
5. Idempotent per subject: recompute replaces OPEN risk for same `(subject_type, subject_id)`; terminal risks never resurrect.
6. Emits internal domain event `risk.calculated { riskId, band, score }` on the bus (orchestrator consumes later).
7. Read APIs for dashboard.

### Scoring rules (defaults; each rule contributes `{ruleId, points, detail}` to factors)

```text
Base = 0, cap 100

payment_failed_count >= 1        +20
payment_failed_count >= 2        +20      (cumulative → +40 at ≥2)
days_overdue >= 3                +15      (invoices)
amount_high                      +10      (≥ ₹50,000 default; tenant-tunable)
customer_active                  +10      (subscription ACTIVE or activity ≤90d)
historical_payment_success       +10      (≥3 succeeded payments)
high_checkout_intent             +15      (payment_started or cart_value ≥ ₹5,000)

band: score<40 LOW | 40–59 MEDIUM | 60–84 HIGH | ≥85 CRITICAL
```

Inputs fetched via repositories only (no raw SQL): failure count from payments/attempts, days overdue from invoices due_at, history aggregates windowed to 180d.

### Processing flow per trigger event

```text
event → load subject aggregate (+customer) → evaluate rules → score/band/factors
      → upsertOpenRisk (idempotent by subject anchor)
      → publish risk.calculated envelope (correlation_id inherited)
      → metric risk_calculations_duration_ms observe; counter by band
```

Closing path: on success-type events, mark matching OPEN risks ASSESSED→EXPIRED (status_reason='resolved_upstream').

## State Transitions

Risk lifecycle:

```text
(none)
  ↓ trigger event
OPEN ──recompute──► OPEN (row replaced, computed_at bumped)
  ├─ success event ──► EXPIRED (resolved_upstream)
  └─ consumed by orchestrator ──► ASSESSED (case attached)
```

## AI Behavior

None. The AI *consumes* risk output later; engine stays deterministic so scores are reproducible in tests and audits (spec 01 §8 "Start deterministic").

## Reliability

- Idempotent recomputation (upsert anchor) makes redelivery harmless.
- Missing referenced entities (e.g., customer deleted): NON_RETRYABLE skip with WARN.
- DB serialization errors → retryable per bus framework.
- Latency target <50ms p95 (spec 03 §10) measured via histogram.

## Security Considerations

Read endpoints tenant-scoped via principal; factor details contain no contact PII.

## Observability

Span `risk.calculate{type,score,band}`; counters by band/type; slow-eval warnings >50ms.

## Tests

Unit (table-driven):
- every rule fires/not-fires at boundary values (counts 0/1/2, overdue 2/3 days, amount at threshold)
- cap-at-100 behavior; band boundaries 39/40/59/60/84/85
- factors array completeness matches fired rules
Integration:
- payment.failed event → OPEN risk with expected score using seeded fixtures
- duplicate delivery → single OPEN risk, no duplicates
- payment.succeeded after failure → risk EXPIRED
- GET /risks filters + tenant isolation (second tenant's data invisible)
Perf smoke: 500 evals < 50ms avg.
