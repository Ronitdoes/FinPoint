# Step 20 — Temporal Foundation (Worker Service, Activity Framework, Testing Harness)

## Objective

Create `services/worker` — the Temporal worker process hosting all recovery workflows and activities — plus the shared client used by the API to start/signal workflows, the activity execution framework (DB tx hygiene, idempotency, heartbeats, retry policies), workflow registry/conventions, and the Temporal test harness for CI.

## Why this step exists

Temporal owns durability: timers, retries, compensation, human waits (spec 02 §2). Every MVP workflow (s-22–24) depends on this substrate. Building it before any business workflow forces correct patterns — activities small and side-effect-explicit ("Never put external network calls directly into workflow code", spec 01 §13) — instead of retrofitting them later.

## Requirements

1. New workspace `services/worker` (root workspaces updated to include `services/*`; turbo tasks extended).
2. Worker binary: connects namespace `revenue-recovery`, task queue `recovery-main`, registers workflows+activities from a registry module; graceful shutdown draining activities.
3. Workflow conventions module:
   - deterministic-only code inside workflow bodies (lint rule banning imports of db/adapters/fetch there)
   - WorkflowId = `recover:{caseId}`, IdReusePolicy=ALLOW_DUPLICATE_FAILED_ONLY, startToClose defaults
   - signals: `pause`, `resume`, `stop`, `human-decision`
4. Activity framework:
   - every activity receives `{tenantId, caseId, ...}` context; opens its own DB tx via repos; NEVER runs inside caller tx
   - standard retry policy: initial 1s, backoff 2.0, jitter FULL, max attempts 3 (activity-level); non-retryable error types declared per activity
   - heartbeat on long loops (status polling)
5. Client wrapper in worker package consumed by API (s-17): `startRecoveryWorkflow`, `signalCase`, `cancelWorkflow` with idempotent start semantics.
6. Activities implemented NOW as the shared library (used by s-22–24):

```text
loadCaseSnapshot          checkPolicyAgain         executeRetryPayment
createPaymentLinkAndStore sendTemplateMessage      refreshPaymentStatus
recordOutcome             createHumanTask          waitForHumanDecision(signal-based)
markCaseWaiting           markCaseInProgress       stopCaseWithReason
appendTimeline            emitMetric               escalateWorkflowFailure
```

7. Test harness: @temporalio/testing TestEnvironment fixtures + fake activity overrides; time-skipping support for timer-heavy flows.

## Technical Implementation

### Files

```text
services/worker/
├── package.json tsconfig.json
└── src/
    ├── worker.ts                 # entrypoint (bun run dev/start)
    ├── client.ts                 # API-side connection singleton (lazy)
    ├── registry.ts               # WORKFLOWS[], ACTIVITIES[]
    ├── framework/
    │   ├── activity-context.ts   # ctx propagation, logging bind, metrics
    │   ├── retry-policies.ts     # named policies
    │   └── errors.ts             # NonRetryable(tagged), TerminalProviderError
    ├── activities/
    │   └── *.ts                  # list above (thin → services in apps/backend domain modules where logic lives;
    │                             #  worker imports service layer from shared packages to avoid duplication)
    ├── workflows/
    │   ├── shared.ts             # const WORKFLOW_ID(caseId), signal names, common sequence helpers
    │   └── _template.ts          # skeleton demonstrating structure + comments contract
    └── testing/
        ├── env.ts                # TestEnvironment bootstrap
        └── mocks.ts              # provider/context fakes
```

Architecture note: business logic stays in packages (`@repo/integrations`, repositories); worker activities are orchestration glue calling that logic. This keeps both API and worker thin over one domain core.

### Retry policy table (named, reused by s-22–24)

```text
STANDARD      : maxAttempts 3, initial 1s, backoff 2.0, jitter FULL
PROVIDER_POLL : maxAttempts 12, initial 10s (heartbeat), for status polling loops
HUMAN_WAIT    : no retry (signal-driven), workflow timeout 30d
NON_RETRYABLE : validation failures, policy rejections, terminal declines, opt-outs
```

### Signal semantics

```text
pause  → workflow enters WAITING (condition flag) — timers keep state, execution suspended at next checkpoint
resume → clears flag
stop   → set stopped reason; workflow unwinds cleanly (no dangling side effects mid-activity; current activity completes)
human-decision {taskId, approved, notes} → resolves pending approval promise
```

## Data Model Changes

None new (workflows/workflow_events rows maintained via activities).

## API Contracts

Internal only (client wrapper). Documented function signatures replace HTTP here:

```ts
startRecoveryWorkflow(input): Promise<{workflowId, accepted}> // idempotent by WorkflowId
signalCase(caseId, signal, payload): Promise<void>
```

## State Transitions

Workflow row: RUNNING→(COMPLETED|FAILED|CANCELLED|CONTINUED_AS_NEW) maintained by recordOutcome/escalate activities; case transitions remain owned by s-17 primitives invoked INSIDE activities.

## AI Behavior

Workflows consume decision records; they may REPLAN (call ai.decide purpose=REPLAN) between rounds via activity — still bounded identically (policy re-check mandatory after every replan).

## Reliability

- Crash-safety: any activity re-executed after crash must be safe → all mutating activities idempotent by design (keys from s-05 anchors).
- Timer correctness under time-skipping tests proves multi-day waits don't stall CI.
- Worker crash mid-activity → Temporal retries per policy; EXECUTING-stuck reconciliation handled by sweeper (s-31).

## Security Considerations

Worker holds same DB creds as API (documented tradeoff MVP) but NO public exposure; provider creds identical boundary rules; workflow inputs contain ids not PII.

## Observability

Interceptors: workflow/activity spans with recovery.case_id etc.; workflow_started_total/outcome counters wired; long-running timer visibility via Temporal UI locally.

## Tests

Harness-level (time-skipped):
- start→signal pause→resume→complete happy skeleton executes in order
- stop during wait terminates with STOPPED reason persisted
- activity retry policy honors maxAttempts/backoff (fake clock)
- duplicate startRecoveryWorkflow same id → single execution (handle returned equal)
- non-retryable error short-circuits retries
- workflow_events rows appended at checkpoints
