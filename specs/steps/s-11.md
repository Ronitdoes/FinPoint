# Step 11 — Internal Event Bus & Replay

## Objective

Implement the `EventBus` abstraction with two drivers — Redpanda (production) and in-process (dev/test fallback) — plus the consumer framework (retry, backoff, dead-letter), and the internal endpoints `POST /events` (authenticated ingestion) and `POST /events/replay`.

## Why this step exists

Spec 01 §0 routes webhooks through Kafka/Redpanda into Risk Engine, Context Service, and Analytics; spec 01 §3 explicitly allows keeping Redpanda optional early. The bus interface decouples those consumers from transport choice, so s-12+ can be built and tested against the in-process driver while production wiring is real from day one. Replay makes the system debuggable and demo-friendly ("re-run this event through the pipeline").

## Requirement Coverage

- Spec 01 §0 architecture (bus between gateway and engines)
- Spec 02 §13 internal event APIs: POST /events, POST /events/replay
- Spec 01 §6 envelope standardization enforced at publish boundary
- Spec 03 §9 failure-injection readiness (consumer retries/DLQ exercised later in s-31)

## Prerequisites

- s-10 (producer side + events table)
- s-02 (Redpanda container), s-09 (auth for /events)

## Requirements

1. `EventBus` interface: `publish(event, opts?)`, `subscribe(topic, group, handler, opts)`; two implementations selected by `EVENT_BUS_DRIVER`.
2. Topics: `revenue-events.v1` (main), `revenue-events.retry`, `revenue-events.dlq`. Consumer groups per consumer role: `risk-engine`, `orchestrator`, `analytics`.
3. Consumer framework: manual offset commit AFTER handler success; retryable error → exponential backoff w/ full jitter (base 1s, factor 2, max 60s, max attempts 5) via retry topic re-publish carrying attempt count header; exhausted → DLQ with error metadata.
4. Poison handling: schema-invalid envelopes → straight to DLQ (no retry).
5. `POST /events`: authenticated (API key scope `events:write`) ingestion of INTERNAL events (e.g., checkout.started from merchant backend) → same validate→store→publish path as webhooks.
6. `POST /events/replay`: re-publish stored event(s) by id/filter; requires OPERATIONS+; writes audit entry.
7. Graceful shutdown: stop fetch, finish in-flight handler, commit, exit.

### Semantics both drivers must share (tested against each)

```text
at-least-once delivery          → consumers must be idempotent (they are: DB anchors)
per-group ordering              → partition key = tenant_id (redpanda); FIFO queue (inprocess)
visibility/lease                → redpanda: commit-after-success; inprocess: no parallel delivery within group
attempt metadata                → headers x-attempt, x-first-seen, x-last-error
DLQ message shape               → { originalEnvelope, error:{code,message}, attempts, firstTopic }
```

### POST /events contract

```text
POST /events
Auth: Bearer API key (scope events:write)
Body:
{
  "type": "checkout.started",           // internal taxonomy only (customer.* also allowed)
  "occurred_at": "ISO",                 // optional, default now
  "source": "INTERNAL",
  "tenant_id": "...",                   // must equal principal tenant unless ADMIN cross-tenant (not allowed MVP)
  "customer_id": "cus_...",             // required for customer-bound types
  "entity_type": "CHECKOUT",
  "entity_id": "chk_...",
  "payload": { ... }                    // validated against per-type payload schemas
}
Responses:
  202 {eventId}                          accepted async
  401/403 auth errors | 422 VALIDATION
Idempotency: caller MAY send Idempotency-Key header → idempotency_keys row (24h TTL);
             same key+different body → 409 IDEMPOTENCY_KEY_REUSED
```

### POST /events/replay contract

```text
POST /events/replay
Auth: session, role ≥ OPERATIONS
Body: { eventId } | { filter: { tenant_id?, type?, from?, to?, status? }, limit ≤ 1000 }
Behavior: marks new event rows referencing originals (replayed_from=id), publishes copies with fresh correlation ids linked via metadata.replay_of
Responses: 202 {queued:n, replayIds:[...]} | 403 FORBIDDEN
Audit: audit_logs entry actor=USER event='events.replayed' metadata={filter|eventId, queued}
```

## State Transitions

Event rows: RECEIVED→PROCESSING→PROCESSED|FAILED; FAILED→(via replay)→RECEIVED again as NEW row (history preserved).

None.

## Reliability

Retry policy table (encode in consumer.ts constants):

```text
handler errors classified:
  RETRYABLE   : network timeouts, broker unavailable, DB serialization/deadlock, 5xx from downstream
  NON_RETRYABLE: validation failure, entity-not-found, policy hard-stop
backoff: delay = min(cap, base * 2^attempt) with full jitter; max 5 attempts → DLQ
DLQ alerts surface in metrics (s-08 counters) and s-34 alerting
```

Crash safety: uncommitted offsets redeliver after crash — safe because every consumer dedupes via DB anchors.

## Security Considerations

- /events authenticated + rate limited (60/min/key default).
- Replay is privileged + audited (prevents silent pipeline manipulation).
- Envelope codec rejects payloads >256KB.

## Observability

Metrics: `bus_published_total{topic}`, `bus_consumed_total{group,status}`, `bus_retry_total{group}`, `bus_dlq_total{group}`. Spans link producer→consumer via trace context propagated through message headers.
