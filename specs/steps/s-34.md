# Step 34 — Monitoring, Alerting & Operations Runbooks

## Objective

Stand up production observability: Prometheus + Grafana (dashboards as code), the alert rule set derived from spec 01 §20/§24 metrics and spec 03 §10 targets, structured log aggregation conventions, and operational runbooks for every alert. Measure and publish actual performance numbers against MVP targets.

## Why this step exists

Spec 01 §20 lists exactly what to instrument; spec 03 §10 sets engineering targets ("Measure actual values rather than claiming them"); Pillar D requires the system to answer "why did the system stop?" in production, not just demos. Metrics exist since s-08 — this step turns them into watched, actionable signals with human procedures attached.

## Requirement Coverage

- Spec 01 §20 instrument list + core trace keys
- Spec 03 §10 performance targets table
- Spec 00 §9 metric catalog → dashboard panels
- Spec 01 §26 monitoring/logging/alerts deployment row

## Prerequisites

- s-08 instrumentation emitting; s-33 staging live producing real traffic patterns

## Requirements

1. Grafana dashboards (JSON in `infra/grafana/dashboards/`, provisioned):
   - **Executive**: Revenue at Risk / Recovered / Recovery Rate / Net / Active Cases / Escalations (from analytics API scrape or DB exporter — implementation: postgres_exporter with analytics views OR scheduled pushgateway snapshot from analytics service; decide+record ADR-016)
   - **Operations**: webhook ingest rate/latency, bus lag & DLQ depth, workflow start/outcome rates, case funnel, provider failure rates, policy rejection rate
   - **AI**: decision latency p50/p95, token usage & cost rate, fallback rate, circuit state, approval queue depth/age
   - **Infra**: HTTP error budget burn, DB connections/pool saturation, Redis memory/hits, Temporal worker pollers/activity slots
2. Alert rules (Prometheus rules file) — every alert names a runbook:

```text
WebhookErrorRate>2% 5m           → page
BusDLQDepth>0 15m                → ticket+slack (poison investigation)
WorkflowFailureRate>1% 15m       → page
ProviderFailureRate>10% per op   → page (provider incident path)
LLMFallbackRate>30% 30m          → warn (degraded autonomy mode)
PolicyRejectionSpike>3σ          → warn (misbehaving recommender or bad rule deploy)
RecoveredAmountDrop vs 7d avg>50%→ warn (silent pipeline break)
P95WebhookLatency>300ms 15m      → warn (target breach, spec 03 §10)
DBPoolSaturation>80%             → warn
TemporalWorkerPollers==0         → page (execution halted!)
AuditWriteFailures>0             → page (immutability regression)
CertExpiry<14d, DiskFills        → ops hygiene set
```

3. Runbooks `docs/runbooks/*.md` one per alert: symptoms → dashboard links → diagnosis steps → mitigation → escalation owner.
4. Log pipeline: structured JSON shipped (Loki or platform-native) with preserved correlation keys; saved queries for "trace this case_id across logs" procedure documented.
5. Performance validation pass: k6/load-lite script driving realistic mix through staging (webhook burst 100/s for 60s, read APIs 50 rps) capturing measured values into docs/PERFORMANCE.md table vs targets:
   webhook <300ms | API reads p95 <500ms | policy <50ms | risk <50ms | LLM <5s typical | zero duplicate financial actions under load.
6. SLO framing: initial SLOs (ingest availability 99.5%, journey success ≥99% weekly) recorded; error-budget policy note (what freezes features if burned).

## Technical Implementation

### Files

```text

```

### Dashboard-data decision (ADR-016)

Business KPIs on Grafana via read-replica-safe path: scheduled job (5min) queries analytics views with service role → pushes to Prometheus pushgateway with tenant=staging|prod labels. Keeps OLTP untouched; numbers identical to dashboard API by construction.

## Data Model Changes

None.

## API Contracts

`GET /metrics` hardened (s-30): network-restricted scrape config documented; no business PII in any exported label (audited).

## State Transitions

Alert lifecycle states documented in runbooks (firing→acknowledged→mitigated→postmortem-link).

## AI Behavior

Degraded-mode doctrine codified: LLMFallbackRate sustained → banner in dashboard settings (ops toggle) noting system operating on deterministic fallbacks — bounded autonomy holds (policy layer unchanged).

## Reliability

Alert evaluation against staging first (avoid noisy prod onboarding); paging thresholds tuned from observed baselines captured in PERFORMANCE.md.

## Security Considerations

Grafana behind auth; anonymous view disabled; runbooks contain no secrets (rotation references only).

## Observability

Meta-monitoring: prometheus self-scrape + alertmanager uptime check — monitoring the monitor.

## Tests

- Rules unit-tested via promtool checks in CI (syntax + no duplicate alerts).
- Synthetic firing drill: force each top-3 page alert in staging → correct routing received (evidence screenshot/log).
- Load script results committed; regressions >20% on any target fail a perf-gate job (nightly).

## Definition of Done

- [ ] Four dashboards live w/ real staging data
- [ ] All alerts routed successfully incl. tested paging path for top incidents
- [ ] 12+ runbooks reviewed (no TBD owners)
- [ ] PERFORMANCE.md populated with MEASURED numbers vs all six targets
- [ ] Load gate running nightly; baseline archived
