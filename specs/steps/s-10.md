# Step 10 — Event Gateway & Webhook Ingestion (Stripe, Razorpay)

## Objective

Implement the provider-facing Event Gateway: `POST /webhooks/stripe` and `POST /webhooks/razorpay` with signature verification, payload normalization into the internal event envelope, database-backed idempotency, fast acknowledgment, and zero business logic in the request path. Also implement the upsert of financial core records (payments/checkouts/invoices/customers) from webhook payloads so the platform has data to reason about.

## Why this step exists

This is the entry point of the whole loop ("an event enters the system", spec 01 goal #1). Spec 02 §2 constrains the gateway strictly: authenticate, normalize, enforce idempotency, publish — never call LLMs, never run workflows, never message customers. Getting the anti-duplication and fast-ack behavior right here is what makes every downstream guarantee possible.

## Requirement Coverage

- Spec 01 §7 Event Gateway (7 responsibilities + "Never run LLM logic inside the webhook request")
- Spec 01 §6 event envelope; spec 02 §5 event taxonomy
- Spec 03 §10 webhook < 300ms acceptance target
- Spec 01 §21 duplicate-webhook idempotency
- Spec 02 §14 webhook signature validation boundary

- s-04/s-05/s-06 (events table + repos with insertEventIfNew)

## Requirements

1. Signature verification per provider (constant-time): Stripe `Stripe-Signature` HMAC-SHA256 over `timestamp.payload` with tolerance window ±5 min; Razorpay `x-razorpay-signature` HMAC-SHA256 over raw body.
2. Raw-body capture (must verify signature against exact bytes — register content-type parser preserving raw body).
3. Normalizers: `stripeNormalizer`, `razorpayNormalizer` mapping provider events → internal envelope types (payment.created/pending/failed/succeeded/refunded/disputed; checkout.* where supported; subscription.*; invoice.*) and → financial-core upserts.
4. Idempotency: UNIQUE `(source, external_event_id)` via insertEventIfNew; duplicates return 200 DUPLICATE without republish.
5. Publish normalized envelope onto EventBus (interface only this step — Redpanda/inprocess implementations arrive in s-11; use inprocess stub).
6. Response within budget: verification+normalize+insert ≤ 300ms p95 locally (publish is fire-and-forget ack).
7. Unsupported event types: store with type=UNMAPPED + metadata.reason, return 200 (never 500 on unknown provider event).

## Technical Implementation

### Files

```text
apps/backend/src/modules/webhooks/
├── routes.ts               # POST /webhooks/stripe | /webhooks/razorpay  (authKind:'webhook')
├── verify-stripe.ts        # constructEvent equivalent using raw body + STRIPE_WEBHOOK_SECRET
├── verify-razorpay.ts      # HMAC check using RAZORPAY_WEBHOOK_SECRET
├── normalize/
│   ├── stripe.ts           # map stripe event.type → envelope; extract customer/payment/checkout/invoice projections
│   ├── razorpay.ts         # map razorpay event (payment.captured/failed, refund.*, subscription.*, invoice.*)
│   └── unmapped.ts
├── ingest.service.ts       # orchestrates: verify→normalize→upsertCore→insertEventIfNew→publish→respond
└── core-upserts.ts         # idempotent upserts into customers/payments/checkouts/invoices keyed by provider refs
packages/integrations/src/events/event-bus.ts   # EventBus interface (producer side) + NullBus placeholder
```

### Processing pipeline (request path)

```text
raw body → signature ok? ──no──► 401 INVALID_SIGNATURE (log WARN w/ ip, provider, reason)
                │yes
                ▼
        normalize (pure fn, may fail → 400 UNMAPPABLE_PAYLOAD stored as FAILED)
                │
                ▼
core upserts (single tx: customer ↔ payment ↔ checkout/invoice links)   ← keeps source-of-truth current
                │
                ▼
insertEventIfNew(events row, raw_payload preserved verbatim)
   ├─ duplicate → 200 {status:'DUPLICATE'}          (metric events_duplicate_total)
   └─ new → enqueue publish → mark PROCESSED after successful bus ack
                │
                ▼
200 {status:'ACCEPTED', eventId}     ← total time budget 300ms
```

Publish failure handling: if bus unavailable, event stays RECEIVED; s-11's dispatcher/replay covers it (never block the webhook response).

### Normalization mapping tables (implement exhaustively for MVP set)

| Provider event | Internal type | Core projection |
|---|---|---|
| stripe `payment_intent.payment_failed` | payment.failed | payments upsert status FAILED (+failure_code/message), attempt row (PROVIDER_AUTO) |
| stripe `payment_intent.succeeded` | payment.succeeded | payments SUCCEEDED, paid_at |
| stripe `charge.refunded` / `payment_intent.amount_capturable_updated` etc. | payment.refunded / pending | respective statuses |
| stripe `charge.dispute.created` | payment.disputed | payments DISPUTED + disputed_at |
| stripe `customer.subscription.*` | subscription.created/renewed/cancelled/payment_failed | subscriptions upsert |
| stripe `invoice.payment_failed/overdue/paid` | invoice.overdue / invoice.paid / … | invoices upsert |
| stripe `checkout.session.completed` | checkout.completed | checkouts upsert |
| razorpay `payment.failed/captured/authorized` | payment.failed / succeeded / pending | payments upsert |
| razorpay `refund.processed` | payment.refunded | payments REFUNDED |
| razorpay `subscription.*` | subscription.* | subscriptions upsert |
| anything else | UNMAPPED | stored, no projection |

Razorpay lacks native checkout-abandonment webhooks — checkout.started arrives via `POST /events` internal ingestion or demo simulator (s-29); document explicitly.

### Customer resolution rule

Provider payloads reference customers by provider ids. Upsert creates a customer record when unseen (`external_ref` = provider customer id). Webhooks lacking any customer binding are stored but skipped for projections (metadata.no_customer=true).

## API Contracts

```text
POST /webhooks/stripe
Headers: Stripe-Signature (required)
Body:    raw Stripe event JSON (verified before parse-trust)
Responses:
  200 {status:'ACCEPTED', eventId}      accepted & published
  200 {status:'DUPLICATE', eventId}     already processed (idempotent redelivery OK)
  400 {error:{code:'UNMAPPABLE_PAYLOAD'}}
  401 {error:{code:'INVALID_SIGNATURE'}}
  406 wrong content-type
Auth: webhook signature ONLY (bypasses session/api-key auth by design)

POST /webhooks/razorpay
Headers: x-razorpay-signature
Same contract as above with razorpay codes.
```

No Idempotency-Key header required — provider event ids ARE the keys (document why).

## State Transitions

Payments: CREATED→PENDING→(FAILED|SUCCEEDED); SUCCEEDED→REFUNDED|DISPUTED. Invoices: DRAFT→SENT→DUE→OVERDUE→PAID|DISPUTED. Checkouts: STARTED→PAYMENT_STARTED→COMPLETED|ABANDONED|EXPIRED. Transitions performed via guarded updates; out-of-order deliveries that would regress status (e.g., succeeded then failed) are ignored with WARN metric `event_order_regression_total`.

None. Enforced structurally: module has no import path to AI code.

## Reliability

Idempotency: DB unique constraint is the arbiter — concurrent identical deliveries race on INSERT; loser reads winner and returns DUPLICATE.
Retries: providers retry non-2xx automatically; our contract returns 200 for anything safely stored, so provider retries only occur for genuine infra failures.
Ordering: envelopes carry occurred_at; consumers resolve conflicts by (occurred_at, status-rank) not arrival order.

## Security Considerations

- Constant-time MAC compare; tolerance window rejects replayed signatures >5min old.
- Raw payloads retained contain provider data only; treat as sensitive (masked in logs; never echoed in errors).
- Endpoint excluded from global rate-limit buckets? No — separate generous bucket (600/min/IP) still applies (abuse prevention, spec 01 §22).

## Observability

## Tests

Unit: signature verify valid/expired/tampered/wrong-secret; each normalizer fixture → expected envelope + projections; unmapped passthrough.
Integration (webhook suite per task requirements):
- valid signature → 200 ACCEPTED, rows created, event PROCESSED
- invalid signature → 401, nothing persisted
- duplicate delivery ×N concurrently → exactly 1 ACCEPTED, rest DUPLICATE, single payment row
- out-of-order (succeeded before failed) → final state SUCCEEDED, regression ignored
- malformed JSON → 400, no crash
- LLM/workflow absence assertion: no ai_decisions/messages rows ever created by gateway tests
Perf smoke: 100 sequential posts < 300ms avg each locally.
