# Step 09 — Authentication, Authorization & Tenant Context

## Objective

Implement user sessions for the dashboard, tenant-scoped API keys for machine access, the RBAC middleware with the five spec roles (ADMIN, FINANCE, OPERATIONS, SUPPORT, VIEWER), and the mandatory tenant-context request decorator that every authenticated route consumes. Seed the first ADMIN user.

## Why this step exists

Spec 01 §22 and spec 03 §11 require API authentication, RBAC, role checks on admin endpoints, and mandatory tenant context. Later endpoints (cases, policies, analytics, human tasks) all declare required roles; that machinery must exist before those routes are written. Provider webhooks deliberately bypass this layer — they authenticate via signatures in s-10.

## Requirement Coverage

- Spec 01 §22: RBAC, API authentication, tenant isolation
- Spec 03 §11: "Tenant context mandatory", "Role checks on admin endpoints"
- Roles list from spec 01 §22

## Prerequisites

- s-04 (users, api_keys tables), s-06 (repos), s-07 (plugin pipeline)

## Requirements

1. Session auth: POST /auth/login, POST /auth/logout, GET /auth/me. Sessions stored server-side (`sessions` table or Redis-backed; recommend Postgres table `user_sessions` for auditability + Redis cache).
2. Password hashing argon2id; login rate-limited per IP+email (lockout backoff).
3. API keys: create/revoke/list endpoints (ADMIN only); bearer token format `rrk_<tenant>_<random>`; verification via sha256 lookup; updates last_used_at.
4. Fastify decorators: `request.auth = { kind: 'session'|'api_key'|'webhook', userId?, tenantId, role, scopes }`.
5. `requireAuth` and `requireRole(...roles)` pre-handlers; route-level declaration convention.
6. Tenant guard helper `getTenantScope(request)` — throws TENANT_CONTEXT_MISSING if absent.
7. Seed script creating demo tenant + admin user via env-provided bootstrap credentials.

### Session design

- `user_sessions` table: id UUID PK, user_id FK, token_hash UNIQUE, expires_at, created_at, ip, user_agent, revoked_at.
- Cookie: httpOnly, Secure (prod), SameSite=Lax, name `rr_session`, TTL 12h sliding renewal.
- Login validates argon2 hash; generic INVALID_CREDENTIALS error (no user enumeration).

### Middleware flow

```text
onRequest: extract cookie|bearer → load principal → decorate request.auth
preHandler: requireAuth / requireRole(...) → 401/403 via error handler
route handler: getTenantScope(request) → pass { tenantId } into services/repos
```

## Data Model Changes

New table **user_sessions** (see above) — added via migration in this step.

## API Contracts

```text
POST /auth/login
  Auth: none (rate limited 5/min/IP)
  Body: { email, password }
  200 → { user: {id,name,email,role,tenantId} } + Set-Cookie
  401 INVALID_CREDENTIALS | 429 RATE_LIMITED

POST /auth/logout            Auth: session → 204 (revokes session)

GET  /auth/me                Auth: session|api_key → principal summary

POST /admin/users            ADMIN  {email,name,password,role} → 201 user
PATCH /admin/users/:id       ADMIN  {role?, status?}
POST /admin/api-keys         ADMIN  {name, scopes?} → 201 {id, key /* raw shown once */, ...}
DELETE /admin/api-keys/:id   ADMIN  → 204
GET  /admin/api-keys         ADMIN  → [{id,name,prefix,lastUsedAt,revokedAt}]
```

All admin routes return FORBIDDEN for non-ADMIN; cross-tenant access impossible because scope comes only from verified principal.

## State Transitions

Session lifecycle: ACTIVE → REVOKED(logout/admin disable) ; API key: ACTIVE → REVOKED. User status DISABLED immediately invalidates sessions (checked at session load).

## AI Behavior

Not applicable.

## Reliability

Login under lockout returns 429 not 401 (prevents timing oracle). Session lookup cached in Redis 60s to keep hot path off DB.

## Security Considerations

- Passwords never logged; key shown exactly once; hashes only in DB.
- Constant-time comparisons for tokens.
- CSRF: dashboard uses SameSite=Lax + JSON content-type requirement; document decision (token-based CSRF deferred until form flows exist — note as future hardening in s-30).

## Observability

Metrics: `auth_logins_total{result}`, `auth_failures_total{reason}`; WARN log on failed login with ip+email-hash.

## Tests

- Unit: permission matrix exhaustive (every role × every action); token hashing round-trip.
- Integration: login→me→logout happy path; wrong password 401; expired session 401; disabled user 401; api-key create/use/revoke; non-admin hitting admin route → 403; missing tenant scope → TENANT_CONTEXT_MISSING.
- Rate-limit integration: 6th rapid login → 429.
