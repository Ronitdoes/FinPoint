# Step 22 — Workflow A: Failed Payment Recovery

## Objective

Implement `FailedPaymentRecoveryWorkflow` end-to-end: the durable sequence message → wait → retry → status check → replan/escalate/stop, consuming approved actions from s-17, executing through s-18/s-19 adapters, recording outcomes via s-26 primitives, and passing the full financial workflow test matrix.

## Why this step exists

Surface 1 is the flagship demo (spec 00 §4) and the workflow named in spec 01 §13/§15. It proves the entire loop — event→risk→case→AI→policy→Temporal→provider→outcome — under durability requirements (crash/restart survival is part of its acceptance).

## Prerequisites

- s-20 framework + activities, s-21 approvals, s-18 payments, s-19 messaging, s-26 outcome recording available as package functions (outcome step may land in parallel; this step defines its consumption contract)

## Requirements

1. Workflow input: `{ caseId }` only — everything else loaded via activities (deterministic replay safety).
2. Execution rounds bounded by policy state (retry_count from DB each round), max 3 retries (POL-MAXRETRY mirrors).
3. Sequence per round:

```text
round:
  loadCaseSnapshot            (status gate: terminal? exit)
  if pending SEND_* actions   → sendTemplateMessage (timeline WHATSAPP_SENT/EMAIL_SENT)
  if RETRY_PAYMENT due        → wait(delay_hours from decision/policy) [skippable in tests]
                                executeRetryPayment → attempt result
                                ├─ SUCCEEDED → recordOutcome → RECOVERED → complete
                                ├─ FAILED    → next round
                                └─ UNKNOWN   → refreshPaymentStatus poll loop → resolve above
  no remaining actions        → evaluate stop vs escalate (replan once) → STOPPED or CREATE_HUMAN_TASK
```

4. Stop conditions checked before EVERY side effect: PAYMENT_SUCCEEDED (event-driven flag via signal/activity re-check), OPTED_OUT, MAX_RETRIES, POLICY_STOP, DISPUTED.
5. Event-reactivity: workflow subscribes to `payment.succeeded` for same obligation via signal bridge (consumer in API signals workflows) so recovery closes instantly on customer paying through original channel rather than waiting timers.
6. Replan path: after final failed retry, one REPLAN ai.decide + policy re-check; allowed outcomes: CREATE_HUMAN_TASK / STOP_CASE / one alternate contact action — never additional retries beyond cap.
7. Outcome recording calls shared `recordOutcome` (s-26): attribution_method=WORKFLOW_LINKED when retried payment succeeded; ATTRIBUTION_WINDOW handled by s-26 sweeper post-close.
8. Every checkpoint appends workflow_events + case timeline entries.

## State Transitions (case-level)

```text
IN_PROGRESS ⇄ WAITING (between rounds / pause signal)
IN_PROGRESS → RECOVERED      (retry success OR external success within attribution window)
IN_PROGRESS → STOPPED        (max retries exhausted & replan says stop / opt-out / dispute)
IN_PROGRESS → ESCALATED      (replan demands human / repeated provider UNKNOWN failures ≥2 rounds)
IN_PROGRESS → FAILED         (workflow infra failure after Temporal retries — swept to human task)
```

## AI Behavior

Consumes initial decision actions; may trigger exactly ONE replan; every executed element must have been ALLOWed by policy at execution time (`checkPolicyAgain` immediately before money/message side effects — state may have changed since opening). Confidence/approval gates inherited from s-16 rules automatically.

## Reliability

Idempotency: retries keyed `{tenant}:{case}:RETRY_PAYMENT:{n}` — crash between claim and call resumes safely; duplicate delivery of external-success signal deduped by case status guard.
Timers: delay_hours honored across worker restarts (Temporal history). Provider timeout path exercised via SIMULATE_PAYMENT_TIMEOUT.
Retry policies: STANDARD on activities; HUMAN_WAIT for approval; PROVIDER_POLL for status.

## Security Considerations

Workflow args carry ids only; decline details stored redacted into timeline (no raw provider payloads).

## Observability

Span per round `workflow.round{n}`; counters workflow_outcome_total{type=failed_payment,result}; time-in-wait histogram (avg time to recovery metric source).

## Tests (harness, time-skipped unless noted)

```text
1. happy path          : msg → wait(24h skipped) → retry SUCCEEDED → RECOVERED + outcome row + timeline complete
2. fail→fail→fail      : 3 rounds then replan(mock) → STOPPED(MAX_RETRIES) ; retry_count never exceeds 3
3. retry then success  : FAILED round1 → SUCCEEDED round2 → RECOVERED
4. permanent failure   : do_not_honor ×3 + replan STOP
5. duplicate execution : same workflow id started twice → single logical run (idempotent start)
6. concurrent attempts : forced parallel activity invocation → second blocked by claim (no double charge)
7. provider timeout    : SIMULATE_PAYMENT_TIMEOUT → UNKNOWN → poll → resolved SUCCEEDED (fake clock)
8. provider error      : 5xx storm → activity retries exhausted → ESCALATED(WORKFLOW_FAILURE task created once)
9. opt-out mid-flight  : signal received between rounds → immediate STOPPED(OPT_OUT), no further sends
10. external success   : original-channel payment lands during WAIT → instant close without consuming retry
11. approval flow      : replan proposes incentive → REQUIRE_APPROVAL → reject → STOPPED(HUMAN_REJECTED)
12. restart survival    : kill worker mid-round (fault point) → resume completes correctly (integration w/ real worker process)
```
