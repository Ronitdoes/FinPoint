# Step 32 — End-to-End Acceptance Tests

## Objective

Implement the complete E2E acceptance suite proving spec 01 §29's eighteen-step definition-of-done journey plus every acceptance test from spec 03 §8, executed against the fully composed stack (real API, DB, Redis, Temporal, Redpanda in-process or broker driver) with mock providers.

## Why this step exists

The MVP is "done" only when the whole loop works: provider event → authenticated → deduped → risk → case → context → AI decision → policy → workflow → message → retry → success → outcome → dashboard number → audit trail — surviving restarts (§29 item 18). Unit/integration/chaos suites prove components; this suite proves the *product promise* continuously.

## Requirement Coverage

- Spec 01 §29 definition of done (18 items) — mapped assertion-by-assertion
- Spec 03 §8 all six acceptance blocks (payment recovery ×4, checkout ×2, invoice ×1)
- Spec 00 §2 "Our system" closed-loop description

## Prerequisites

- s-22–s-29 functional completeness; s-31 harness utilities reused

## Requirements

1. Suite runner boots full compose profile `e2e` (fresh volumes), applies migrations, seeds minimal deterministic fixture set (NOT the full s-29 volume — speed), starts API+worker, waits ready.
2. Journey test (the flagship): scripted payment-failure simulation through to dashboard-visible recovery:

```text
1. POST /demo/payment-fail (CUS-001 scenario A shape)
2. assert webhook auth path used (signed loopback)
3. replay same delivery → duplicate ignored (no second case)
4. internal event row exists w/ normalized envelope
5. risk calculated HIGH (0.86-parity fixture)
6. exactly one recovery case RC-* DETECTED→…
7. context snapshot stored on decision matches allowlist schema
8. ai_decisions row COMPLETED w/ schema-valid output (or FALLBACK badge if injection on)
9. policy_evaluations row ALLOWED for executed actions
10. workflows row RUNNING; Temporal UI/history queryable via SDK
11. message ledger shows WhatsApp SENT (mock) idempotent-keyed
12. attempt row REQUESTED then provider called once
13. /demo/payment-succeed → SUCCEEDED propagates
14. outcome row recorded w/ recovered_amount=12999, method WORKFLOW_LINKED
15. net = recovered − costs (LLM+messaging entries exist)
16. GET /analytics/summary reflects ₹12,999 recovered (cache-bust verified)
17. timeline contains ≥9 required entry types in order
18. kill -9 API + worker mid-wait earlier in a variant run → journey still completes (restart resilience §29#18)
```

3. Spec 03 §8 block tests implemented verbatim as named cases (Given/When/Then preserved in titles).
4. Dashboard assertion layer: Playwright against built frontend verifying overview card delta and case-timeline render post-journey (closes UI loop).
5. Runtime budget: full suite ≤10min CI wall clock (time-skipping where safe; real timers only for restart variant).
