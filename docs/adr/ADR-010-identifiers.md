# ADR-010 — Identifier strategy: UUIDv4 PKs, bigserial logs, human case numbers

- **Status:** Accepted
- **Date:** 2026-08-25
- **Deciders:** Engineering (step s-01)
- **Related specs:** `specs/02-architecture-and-domain.md` §3 (`RC-123` display id)

## Context

Business rows need globally unique IDs safe to generate on any node (webhook normalizers, workers); append-only tables need cheap monotonic ordering; humans need readable case references like `RC-123` (spec 02 §3).

## Decision

1. Business primary keys use **UUIDv4** generated by PostgreSQL `gen_random_uuid()` defaults (application may also supply UUIDs for idempotent inserts).
2. Append-only log/event tables (raw events, audit logs, workflow events) additionally carry a **`bigserial` sequence** for stable insertion order and cursor-based pagination/replay.
3. Every recovery case gets a human-readable case number `RC-{per-tenant sequence}` assigned at creation inside the same transaction as the row insert (per-tenant Postgres sequences or counter table with guarded increment). It is unique per tenant and used for display/search only — never as join key or foreign key.
4. External provider IDs (Stripe/Razorpay object ids) are stored in dedicated `provider_*_id` columns with tenant+provider-scoped uniqueness where applicable.

## Consequences

- No coordination needed to mint business IDs; joins stay on fixed-width UUIDs.
- Replay/audit queries can rely on monotonic bigserial ordering even under clock skew.

## Alternatives considered

- **Sequential bigint everywhere:** rejected; leaks volume, complicates multi-node inserts.
- **Human number as PK:** rejected; format churn risk and cross-tenant collisions.
